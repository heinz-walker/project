<h1>Slack 워크스페이스 보안 현황 점검</h1>
<i>Slack Workspace Security Assessment</i>
</div>

*2025.02 · 정보보안 담당*

---

## 1. 요약
관리자 콘솔 캡처와 전체 계정 내보내기 데이터를 근거로 Slack 워크스페이스의 보안 설정을 처음부터 끝까지 점검했다.
관리자 고문(Admin Advisor) 화면에서 외부 조직과 연결된 협업 채널이 예상보다 많다는 신호를 확인한 뒤, 관련 설정 화면을 교차 확인해 그 구조적 원인을 규명했다.
계정 데이터를 인증 방식별로 집계해 정책 문서만으로는 보이지 않던 관리자 권한 계정의 인증 이중화 공백과 게스트 계정 관리 공백도 함께 찾아냈다.
확인된 항목은 조치 권한(관리자 즉시 조치 가능/워크스페이스 소유자 승인 필요/요금제 제약)별로 나눠 보고서로 정리했다.

---

## 2. 배경
인프라 쪽 보안 통제(네트워크, 클라우드 계정, 서버)는 정기적으로 점검해왔지만, 사내 메신저인 Slack은 SaaS 관리자 콘솔 안에 있어 같은 점검 루틴에 포함되지 않고 있었다.
Slack은 임직원 전원이 매일 쓰고 외부 파트너와의 접점(채널 공유, 다이렉트 메시지)도 있어, 설정 하나의 기본값이 조직 전체의 외부 노출 범위를 바꿀 수 있는 영역이다.
그래서 이번에 별도로 시간을 내어 관리자 콘솔을 처음부터 끝까지 점검하기로 했다.

---

## 3. 담당 역할
- 점검 방법론 설계 — 관리자 콘솔 캡처와 전체 계정 내보내기(CSV) 데이터를 교차 검증하는 방식으로 점검 절차 수립
- 전 영역 점검 — 인증·세션, 외부 협업(Slack Connect), 앱/통합, 계정·권한, 감사/데이터 보존 항목별 현황 확인
- 근본원인 추적 — 외부 협업 기능이 확산된 원인을 설정 화면 교차 확인으로 규명
- 결과 보고 — 조치 권한별로 항목을 분류해 우선순위 조치안 작성 및 보고

---

## 4. 진행 과정
### 4.1. 점검 방법론 설계
> 관리자 콘솔 화면 캡처만으로는 전체 계정의 실제 인증 현황을 알 수 없어서, 콘솔 확인과 계정 데이터 내보내기 분석을 함께 쓰는 방식으로 설계했다.

관리자 고문이 항목별 권장사항을 보여주긴 하지만, 그 결과가 "왜" 그런 상태인지, 실제 영향 범위가 얼마나 되는지는 알려주지 않는다.
그래서 권장사항 화면은 점검 항목을 놓치지 않기 위한 체크리스트로만 쓰고, 실제 판단은 설정 화면 하나하나를 열어 현재값과 편집 권한(워크스페이스 관리자 vs 소유자)을 직접 확인하는 방식으로 진행했다.
인증 방식 비율, 게스트 계정 현황처럼 계정 단위 통계가 필요한 항목은 전체 계정을 CSV로 내보내 별도로 집계했다.

### 4.2. 외부 협업 기능 확산의 구조적 원인 추적
> 외부 조직과 연결된 채널 수가 예상보다 많다는 것을 확인한 뒤, 그 원인을 설정 화면 3개를 교차 확인해 구조적 허점으로 규명했다.

관리자 고문 화면에서 외부 조직과 연결된 협업 채널(Slack Connect)이 예상보다 많다는 신호를 먼저 확인했다.
연결 목록만 봐서는 "왜 이렇게 많아졌는지"를 알 수 없어서, 관련 정책 설정 화면을 하나씩 열어 원인을 역추적했다.
그 결과 세 가지 설정이 겹쳐 있었다: 게스트를 제외한 전 직원이 채널·워크플로·앱 전체 접근 권한까지 포함한 강한 초대를 승인 없이 보낼 수 있었고, 채널 초대 승인이 필요한 조건이 "기존 채널(생성 후 24시간 경과)"로 한정돼 있어 새로 만든 채널로 외부 조직을 초대하면 애초에 승인 절차를 타지 않았으며, 연계되지 않은 외부 조직 사람과의 다이렉트 메시지도 전 직원이 승인 없이 주고받을 수 있었다.
승인 권한자 자체는 소유자·관리자로 제한돼 있어 문제가 없었다 — 문제는 애초에 승인이 필요한 범위가 좁게 설계돼 있었다는 점이었다.
이렇게 규명한 원인 덕분에 보고서에는 "외부 연결이 많다"가 아니라 "어떤 설정 세 가지를 바꾸면 근본적으로 해소되는가"를 담을 수 있었다.

### 4.3. 계정·권한 현황 분석
> 전체 계정을 인증 방식별로 집계해, 정책 문서만으로는 보이지 않던 관리자 권한 계정의 인증 공백과 관리 사각지대를 찾아냈다.

계정 내보내기를 인증 방식별로 집계한 결과, 실사용 활성 계정 중 SSO·2FA 중 아무것도 없는 계정은 0명으로 기본 인증 정책 자체는 잘 지켜지고 있었다.
다만 최고 권한군(소유자·관리자) 계정 중 상당수가 SSO 단일 인증에만 의존하고 있어, SSO 계정 하나가 뚫리면 곧바로 최고 권한까지 노출되는 구조라는 점을 확인했다 — 권한이 높을수록 인증 수단은 이중화돼야 한다는 원칙이 실제로는 지켜지지 않고 있었다.
싱글채널 게스트 계정 전원이 만료일 없이 등록돼 있어 협업 목적이 끝난 뒤에도 무기한 접근이 가능한 상태였고, 봇·비활성 계정이 전체의 절반을 넘어 계정 정리 자체도 별도 과제로 남았다.

---

## 5. 성과 및 배운 점
- "외부 조직 연결이 많다"는 표면적 관찰을 설정 화면 교차 확인으로 근본원인(승인 예외 조건 세 가지)까지 추적해, 개별 채널을 하나씩 정리하는 대신 설정 세 가지를 바꾸는 것으로 재발을 막을 수 있는 형태의 개선안을 만들었다.
- 관리자 콘솔의 자체 진단 기능(Admin Advisor)은 점검 항목을 놓치지 않게 해주는 체크리스트로는 유용하지만, "왜 그런 상태가 됐는지"는 설정 화면을 직접 열어 확인해야 알 수 있다는 것을 확인했다.
- 계정 데이터를 인증 방식·역할 기준으로 집계하는 방식이 정책 문서만으로는 보이지 않는 실제 공백(권한 계정의 인증 이중화 공백, 게스트 계정 만료 미설정)을 드러내는 데 효과적이었다.
- SaaS 협업도구는 인프라 보안 점검 루틴에 포함되지 않기 쉬운 영역이라는 것을 실제로 확인했고, 이후 정기 점검 대상에 포함하기로 했다.
