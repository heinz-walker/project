## 1. 요약
Live VPC에 설계해둔 Network Firewall·Security Group 표준([04. Live 환경 적용 계획](./04-live-environment-migration-plan.md))을 실제 트래픽 위에서 컷오버한 시도다.
사전 작업으로 SG 33개 중 deploy 계열을 제외한 전 역할을 신규 단일 SG 구조로 전환하고(2-2-1–31), 신규 NLB·로깅을 구축하고, Stage에서 Stateful Default Action Drop 전환을 미리 검증했다.
점검 당일에는 서버 교체 → SG 적용 → 애플리케이션 기동 → 라우팅 테이블/방화벽 인라인 전환(2-1-1–5)까지 진행했으나, 이어지는 검증 단계에서 GS·router 두 서비스에 장애가 겹쳐 확인됐다.
두 장애 모두 방화벽 로그·로컬 재현 결과로 인프라 문제가 아님을 확인했지만, 원인이 완전히 규명되지 않은 채였기 때문에 안전을 우선해 방화벽 인라인 라우팅 3건(2-1-3–5)만 롤백하고 점검을 종료했다.
서브넷 연결과 신규 AZ 전용 NAT(2-1-1/2-1-2)는 리스크가 낮다고 판단해 롤백하지 않고 그대로 남겨뒀다.

---

## 2. 배경
[01](./01-dev-environment-migration.md)–[04](./04-live-environment-migration-plan.md)번 문서에서 Dev·Stage를 거쳐 Live의 표준 아키텍처와 Gap을 이미 정리해뒀고, 04번 문서 8절에는 실행 절차 초안까지 나와 있었다.
남은 문제는 그 초안이 "실제로 실행된 적 없는 계획"이라는 점이었다 — Live는 실서비스 트래픽이 흐르는 환경이라, 계획대로 되지 않을 경우 되돌릴 방법을 미리 준비해두지 않으면 계획 자체가 무의미했다.
이 프로젝트는 그 마지막 단계, 즉 설계를 실제 트래픽 위에서 컷오버하는 실행 프로젝트다.
사전 작업(라이브 영향 없는 준비)과 점검 당일 작업(저트래픽 시간대, 되돌리기 어려운 구간)을 처음부터 분리해서 관리했고, 문제가 생겼을 때 무엇을 근거로 롤백할지를 작업 시작 전에 이미 정해뒀다.

---

## 3. 담당 역할
- SG·Network Firewall 컷오버 실행 계획 수립 및 실제 수행(라우팅 테이블/SG/타겟그룹 전환)
- 롤백 참고 자료(SG 규칙 전문, 리소스별 부착 SG, Route Table 라우트) 사전 스냅샷 확보
- 컷오버 당일 발생한 장애의 인프라/애플리케이션 레벨 원인 구분 진단
- 롤백 여부 결정 및 실행, 사후보고서(포스트모템) 작성

## 4. 진행 과정
### 4.1. 사전 작업 — 되돌리기 어려운 구간을 최대한 비워두기
> 점검 당일에는 라우팅 테이블/방화벽 전환처럼 정말 되돌리기 어려운 작업만 남기고, 나머지는 전부 라이브 영향 없는 시점에 앞당겨 끝냈다.

SG 33개(레거시 12·신규 SG-to-SG 17·계정 공용 4) 중 신규 구조는 이미 만들어져 있었지만 실제 트래픽은 여전히 레거시와 계정 `default` SG로 흐르고 있었다(04번 문서 10절).
사전 작업에서 레거시→신규 매핑표를 만들고 리소스별로 신규 SG를 추가 부착한 뒤 정상 동작을 확인하는 방식으로, deploy 역할을 제외한 전 역할(admin/play/gw/router/msg/gs/memcached/redis/mysql)의 전환을 마쳤다.
deploy는 체크리스트 범위에서 애초에 빠져 있던 항목이라 이번에는 손대지 않고 넘겼다.

기존 msg/router NLB에는 Security Group 자체가 없었다 — AWS는 이미 생성된 NLB에 SG를 나중에 붙일 수 없다는 제약이 있어, 신규 SG로 옮기려면 NLB를 새로 만들어 트래픽을 이관하는 방법뿐이었다.
이 과정에서 신규 SG 체계에 대응하는 내부 로드밸런서 중 일부(msg 내부 NLB, GS 내부 ALB)가 애초에 빠져 있던 것도 함께 발견해 신규로 만들어 채웠다.
로깅(FLOW/ALERT CloudWatch Logs)도 인라인 전환 전에 미리 구축해뒀다 — 전환 즉시 로그로 확인할 수 있어야 "방화벽이 막았는지"를 컷오버 당일에 바로 판별할 수 있기 때문이다.

가장 리스크가 컸던 사전 검증은 Stage에서 미리 해본 Stateful Default Action Drop 전환이었다.
1차 시도에서 시간당 27,503건이 차단됐고, 원인은 두 가지였다 — 외부 TLS 호출 도메인이 allowlist에 없던 것과, 게임 서버 간 통신 프로토콜(포트 13000대) 트래픽의 절반 이상이 TLS/HTTP 어느 쪽으로도 파싱되지 않는 자체 프로토콜이라 도메인 기반 규칙 자체가 매치될 수 없던 것이었다.
2차 시도에서는 도메인이 allowlist에 정확히 등록돼 있어도 SNI 파싱 타이밍 문제로 admin 계열 ALB 트래픽이 오탐 차단되는 별도 문제까지 발견됐다.
두 문제 모두 도메인 검사보다 먼저 평가되는 5-tuple 기반 pass 규칙을 우선순위 1로 추가하는 방식으로 해결했고, Live에도 같은 규칙을 반영한 뒤에야 컷오버를 진행했다.
Live의 Drop 전환 자체도, 방화벽이 아직 인라인되지 않아 트래픽 영향이 없다는 걸 확인하고 사전 작업으로 앞당겼다.

### 4.2. 점검 당일 실행 — 라우팅/방화벽 전환은 순서를 고정
점검 당일 실행 순서는 보안팀 체크리스트와 운영/개발팀 시나리오를 하나로 합쳐 재구성했다.
운영팀이 준비한 원래 시나리오에는 순서 오류가 있었다 — 방화벽이 인라인되기 전에 서버 교체를 먼저 끝내야 한다는 전제 없이 인프라 설정을 서버 교체보다 앞에 두고 있었다.
이를 서버 교체·SG 적용(병렬 가능) → 애플리케이션 기동·신규 타겟그룹 자동 등록 확인 → 라우팅 테이블/방화벽 인라인 전환(순서 고정) → NLB 트래픽 전환 → 최종 검증 순으로 재구성했다.
서버 쪽 문제를 방화벽 인라인 전에 먼저 걸러둬야, 이후 단계에서 문제가 생겼을 때 "서버 문제냐 방화벽 문제냐"가 섞이지 않기 때문이다.

착수 전에는 헬스체크·라우팅 상태를 스크립트로 스냅샷 떠서 작업 전 기준선을 확보했다.
이후 서버 교체와 SG 전환을 마치고, 라우팅 테이블 작업(Public2 서브넷 연결 → AZ-B 전용 NAT 교체 → firewall1/firewall2 endpoint 전환 → IGW Edge association)을 순서대로 진행했다.
firewall endpoint 전환은 응답 트래픽도 같은 route table을 다시 타는 구간이라 가장 리스크가 큰 단계였고, 각 단계마다 대상 서비스의 정상 동작을 즉시 확인하며 진행했다.

### 4.3. 장애 발생과 진단 — 인프라 문제인지부터 구분
> 장애가 두 개 겹쳤을 때 먼저 판단해야 했던 건 원인이 아니라 "이게 방화벽 탓인가"였다.

방화벽 인라인 전환 이후 GS와 router 두 서비스에서 동시에 이상이 확인됐다.
둘 다 곧바로 롤백부터 하지 않고, 방화벽이 원인인지부터 확인하는 절차를 먼저 밟았다.

| 서비스 | 증상 | 인프라 배제 근거 | 결론 |
| --- | --- | --- | --- |
| GS | 실 트래픽 타겟그룹 전체 unhealthy, PHP-FPM 워커 전부 hang | 방화벽이 관여할 수 없는 localhost 요청도 동일하게 hang, 방화벽 alert 로그에 해당 포트 차단 0건, Redis는 `ping` 즉시 응답(엔진 자체는 정상) | 애플리케이션 레벨 문제(워커 풀 설정 `pm.max_children=5` 과소 추정)로 결론, 이후 원인 불명 상태로 자연 회복 |
| router | NLB 헬스체크가 임계값(연속 5회, 최소 2분 30초) 이상 지나도 계속 unhealthy | 로컬 TCP 연결은 0.003초 만에 즉시 성공, 방화벽 alert 로그에 해당 포트 차단 0건, SG·AZ 매칭 정상 | 원인 불명, 미해결 상태로 점검 종료 |

GS는 로컬 `curl` 요청조차 응답하지 않는 것으로 봐서 방화벽이 개입할 수 없는 구간에서부터 이미 문제가 있었고, PHP-FPM 로그에 워커 풀 고갈 경고가 남아 있어 애플리케이션 레벨 문제로 판단했다.
router는 반대로 로컬 기준으로는 모든 게 정상으로 보였다 — 프로세스도, 포트 리스닝도, TCP 연결도 문제없었는데 NLB만 계속 unhealthy로 판정했다.
두 장애 모두 방화벽 alert 로그에 해당 포트 차단 기록이 없다는 공통된 근거로 인프라 문제는 아니라고 확인했지만, router 쪽은 그 이상으로 원인을 좁히지 못했다.

### 4.4. 롤백 결정과 실행
> 인프라 문제가 아니라고 확인됐어도, 원인이 완전히 규명되지 않은 채로 장애가 두 건 겹친 시점에는 되돌릴 수 있는 것부터 되돌리는 게 맞는 판단이라고 봤다.

router 장애의 원인이 끝내 좁혀지지 않은 상태에서, GS 장애까지 겹쳐 있는 시점에 계속 진행하는 것은 리스크가 크다고 판단해 롤백을 결정했다.
롤백 대상은 방화벽 인라인 전환의 핵심인 라우팅 3건(firewall1/firewall2 endpoint 전환, IGW Edge association)으로 한정했다 — 서브넷 연결과 신규 AZ 전용 NAT은 그 자체로 트래픽 차단 기능이 없어 리스크가 낮다고 보고 그대로 뒀다.
사전에 확보해둔 Route Table 스냅샷 덕분에 "원래 target이 정확히 무엇이었는지"를 다시 조사할 필요 없이 즉시 IGW로 되돌릴 수 있었고, 롤백 직후 재조회로 대상 라우팅이 정확히 원상태(IGW 직결)로 돌아갔음을 확인했다.
롤백 이후에도 GS는 원인 불명인 채 자연 회복됐고 router는 계속 unhealthy 상태였다 — 방화벽 롤백과 시점은 겹쳤지만 인과관계는 아니라는 방증으로 봤다.

## 5. 성과 및 배운 점
- 사전에 확보해둔 SG 규칙 전문·리소스별 부착 SG·Route Table 스냅샷 세 문서 덕분에, 장애 상황에서 재조사 없이 대조만으로 롤백 대상과 원상태를 즉시 확정할 수 있었다.
- Stage 사전 검증에서 시간당 27,503건 차단이라는 실패를 먼저 겪어둔 덕분에, 게임 서버 간 통신 프로토콜 미매치와 admin ALB SNI 파싱 타이밍 문제를 5-tuple 우선순위 규칙 2건으로 미리 해결하고 Live 컷오버에 들어갈 수 있었다.
- 로컬 재현·엔진 자체 응답 확인(Redis `ping`)·방화벽 로그 차단 건수 세 가지를 교차 확인해 "인프라 문제가 아니다"를 판별하는 절차를 실제 장애 상황에서 적용했다.
- 실패를 감추지 않고 사후보고서를 남기는 방식으로 프로젝트를 운영했다 — 이번 시도의 문서 일체를 실패 사실이 드러나는 폴더명으로 분리 보관하고, 다음 재시도는 이어서 고치는 대신 새 문서로 처음부터 다시 진행하기로 했다.
- 남은 과제: router NLB 헬스체크 실패의 근본 원인 규명(다음 점검 최우선 조사 대상), deploy SG 전환 미완료(레거시 SG 잔존), 그리고 이번 컷오버 스코프 밖이었던 인터넷 노출 ALB 리스너 룰·WAF 연결 여부(브랜드 간 설정 불일치, source-ip 제한이 default 룰에 의해 무력화되는 문제 등)에 대한 별도 정기 감사 도입.
