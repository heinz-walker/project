## 1. 요약
[05. Live 방화벽 인라인 전환 시도와 롤백](./05-live-cutover-attempt-and-rollback.md) 이후 Live를 다시 전환하기 위해, 계획서를 고쳐 쓰는 대신 Live와 Stage를 AWS CLI로 직접 조회해 차이를 새로 정리했다.
이 diff를 기준으로 서비스 영향이 없는 작업(SG 정리, Cloudflare Tunnel 구성, 방화벽 정책 정렬)을 점검 전에 모두 끝내고, 점검 당일에는 ALB 이관과 라우팅 전환만 남겼다.
점검 체크리스트를 7개 절로 줄이고, 완료 여부를 사람이 눈으로 판단하지 않도록 Stage와 Live를 항목별로 비교하는 조회 스크립트를 함께 만들었다.
결과적으로 사전 작업에서 고아(orphan) 레거시 SG 12개와 deploy 계열 레거시 SG 2개를 삭제해 Stage와 SG 구성을 맞췄고, 점검 당일에는 ALB 12개 중 10개를 이관한 뒤 방화벽 인라인 라우팅 3건을 전환했다.

## 2. 배경
05번의 첫 시도는 사전 작업까지는 계획대로 갔지만, 점검 당일 원인 불명 장애가 겹쳐 방화벽 라우팅을 롤백했다.
다시 시도하려면 "계획서가 현재 Live와 맞는가"부터 의심해야 했다.
Live는 그사이 SG와 서브넷, LB 구성이 바뀌었을 수 있었고, 기존 계획서는 Stage 적용 경험이 쌓이기 전에 쓴 문서였다.
그래서 이번에는 계획서를 이어서 고치지 않고, 현재 상태를 조회해서 Stage와의 차이(diff)를 다시 만든 뒤 그 diff를 작업 목록의 유일한 근거로 삼았다.

## 3. 담당 역할
- Live/Stage 전 영역(서브넷, 라우팅 테이블, NAT, 방화벽 정책, SG, LB, VPC 엔드포인트, EC2) 조회와 diff 작성
- 사전 작업과 점검 당일 작업의 분리, 점검 체크리스트와 콘솔 작업 가이드 작성
- 레거시 리소스(SG, NLB)의 실사용 여부 검증과 정리
- 체크리스트 완료 판정용 조회 스크립트(Stage/Live 비교, 항목별 확인) 개발

## 4. 진행 과정
### 4.1. 계획서 대신 diff로 시작
> 조치 여부를 "문서에 적힌 상태"가 아니라 "조회한 상태"로만 판단하기로 했다.

Live와 Stage를 같은 시점에 조회해 영역별 차이와 조치 항목 목록을 만들었다.
핵심 발견은 세 가지였다.
첫째, Live는 방화벽이 인라인되지 않았고(public 서브넷 라우팅이 IGW 직결), ALB 전용 서브넷이 없었다.
둘째, admin 접속용 Cloudflare Tunnel은 EC2만 있고 SG 규칙, 내부 ALB, 방화벽 정책, 도메인 allowlist가 모두 비어 있었다.
셋째, 새 서버를 만들 필요는 거의 없었고 SG, 방화벽, LB 배선만 맞추면 되는 항목이 대부분이었다.
이후 모든 작업은 이 diff의 항목 단위로 진행했고, 항목을 끝낼 때마다 다시 조회해 Stage와 일치하는지 확인했다.

### 4.2. 레거시 SG 정리 — "안 쓰는 것 같다"를 확인으로 바꾸기
> 규칙만 넓게 열려 있는 SG 12개가 실제로 아무것도 붙어 있지 않은지 네트워크 인터페이스 기준으로 확인한 뒤 삭제했다.

레거시 SG 중 12개는 규칙이 넓게 열려 있었지만, SG 이름만 보고 지우면 연결된 리소스를 끊을 위험이 있었다.
네트워크 인터페이스, ElastiCache, RDS의 SG 부착 정보를 조회해 이 12개에 연결된 리소스가 0개임을 확인했고, 처음 분류가 틀렸던 부분(사용 중이라 봤던 SG 일부가 실제로는 고아)도 이 조회로 바로잡았다.
반대로 계속 쓰이던 레거시 SG 2개(deploy 계열)는 별도로 다뤘다.

이 2개를 지우는 순서에서 계획서의 결함을 하나 찾았다.
기존 순서는 deploy 서버의 SG를 교체한 뒤에 서비스 SG에 새 허용 규칙을 추가했는데, 그 사이에는 배포 SSH가 끊긴다.
순서를 "새 규칙 일괄 추가 → 인스턴스 SG 교체 → 동작 확인 → 기존 규칙 삭제 → legacy SG 삭제"로 바꿨다.
삭제 직전에는 리전 전체 SG 규칙 참조, ENI, Launch Template 사용 여부를 다시 확인했다.
CI 러너가 legacy SG에 의존하고 있던 것도 이 확인에서 드러나, 신규 SG 허용 규칙에 러너를 추가했다.

### 4.3. 점검 체크리스트 — 순서가 곧 안전장치
> 방화벽을 인라인하기 전에 끝나야 하는 것과, 인라인 후에 해도 되는 것을 구분해 순서를 고정했다.

점검 당일 작업은 Interface VPC Endpoint 생성 → 방화벽 allowlist 정리 → 레거시 NLB 정리 → ALB 이관 → public 라우팅 테이블 보강 → 방화벽 인라인 → 종료 전 확인, 7개 절로 정리했다.
순서를 고정한 근거는 다음과 같다.

| 선행 작업 | 선행해야 하는 이유 |
| --- | --- |
| ALB 이관 | 이관되지 않은 ALB가 public 서브넷에 남으면 인라인 후 인터넷에서 ALB로 들어오는 HTTPS가 방화벽을 지나는데, allowlist는 내부에서 외부로 나가는 방향만 허용해 차단된다. |
| IGW 엣지 연결 | 엣지 연결 없이 public 라우팅 테이블만 바꾸면 응답 경로가 어긋나는 비대칭 경로가 생긴다([02. Return Path 설계 원칙](./02-return-path-design-principle.md)). Stage는 연결돼 있었고 Live는 라우트만 있고 연결이 없었다. |
| public 라우팅 테이블에 Gateway Endpoint 연결 | 연결이 없으면 인라인 후 S3 요청이 방화벽 allowlist에 막힌다. |
| Stateless 규칙과 기본 액션 정렬 | Stage에는 있고 Live에는 없던 게임 서버 간 통신용 pass 규칙을 사전에 맞췄다. 05번에서 Stage가 겪은 대량 차단을 반복하지 않기 위해서다. |

체크리스트를 쓰면서 Stage와 Live의 같은 항목을 다시 비교했고, 이 과정에서 위 두 번째, 세 번째 누락을 찾아 추가했다.
레거시 NLB 삭제는 실사용 여부가 불확실해서 Flow Log로 먼저 판단했다.
최근 14일 NLB 트래픽을 IP별로 집계한 결과 779개 IP, 약 589KB가 전부 스캐너로 분류됐고, 같은 기간 신규 NLB 트래픽은 약 13.5GB였다.
삭제 방지가 켜져 있던 LB 6개는 체크리스트에 해제 단계를 추가했다.

방화벽 인라인 후 외부 NTP(UDP 123)가 막혀 시간 동기화가 깨질 수 있다는 우려도 있었다.
AMI 묶음 7종별로 시간 동기화 상태를 확인하니 모두 Amazon Time Sync를 기준 서버로 쓰고 있어, 방화벽 규칙을 추가하지 않기로 했다.

### 4.4. 완료 판정 스크립트 — 판정 도구도 검증 대상
> 체크리스트의 완료 여부를 조회로 판정하는 스크립트를 만들고, 이미 목표 상태인 Stage에 먼저 돌려 스크립트 자체를 검증했다.

점검 중에는 "된 것 같다"가 가장 위험한 판단이라, 항목 1–7을 Stage와 Live에서 비교해 일치/불일치로 출력하는 스크립트(조회 전용)를 만들었다.
처음 버전은 Stage에 돌리자 이미 있는 Interface Endpoint 3개를 모두 "없음"으로 판정했다. 엔드포인트를 만들어도 영원히 불일치로 나오는 버그였다.
같은 방식으로 IGW 엣지 연결을 보지 않아 비대칭 상태도 "일치"로 표시될 수 있는 문제, ALB가 목록에서 사라지면 "이관됨"으로 세는 문제를 찾아 판정 로직을 다시 썼다.
항목별로 확인할 수 있는 조회(엔드포인트 ENI의 443 REJECT, 서버 API 호출 경로, 방화벽 지표, 내부발 blocked 도메인, 내부발 REJECT 급증)도 별도 스크립트 6개로 분리했다.
서버 내부 명령이 필요한 확인은 조회 전용 원칙에 맞지 않아 제외하고, 호출 경로 이력으로 대체했다.

### 4.5. 점검 당일
> 점검 당일에는 ALB 이관과 라우팅 전환만 남겨 두었다.

사전 작업이 끝난 시점에 Live SG는 Stage와 이름 구성이 같아졌고(레거시, 고아 SG 0개), 방화벽 정책, 도메인 allowlist 41개, stateless 규칙 5개, 내부 admin 타겟그룹 3개도 Stage와 일치했다.
당일에는 ALB 12개 중 10개를 ALB 전용 서브넷으로 이관했다. 나머지 2개는 새 ALB로 대체되어 삭제 예정이라 이관 대상에서 뺐다.
이어서 public 라우팅 테이블 2개의 기본 경로를 IGW에서 방화벽 엔드포인트로 바꾸고 IGW 엣지 연결을 추가했다.
원복은 이 세 변경을 반대로 되돌리는 것으로 미리 정해 두었다.
ALB 이관 약 1시간 뒤 공용 SG의 인바운드가 삭제되면서 외부 요청 차단이 발생했고, 이 건은 [08](./08-shared-sg-change-and-partner-callback-outage.md)에서 별도로 다룬다.

## 5. 성과 및 배운 점
- 고아 SG 12개와 deploy 계열 레거시 SG 2개를 연결 리소스 0개 확인 후 삭제했고, 신규 SG를 더한 Live의 SG 구성이 Stage와 같아졌다(레거시, 고아 SG 0개).
- 점검 당일 남은 작업을 7개 절로 줄였고, 서비스 영향이 없는 작업은 모두 사전에 끝냈다. 05번 시도에서는 점검 당일에 SG 전환과 서버 교체까지 몰려 있었다.
- 스크립트를 Stage에 먼저 돌려 판정 로직 버그 3건을 점검 전에 찾았다. 조회 도구도 검증하지 않으면 틀린 "일치"를 만든다.
- 계획서 순서의 결함(배포 SSH 단절, 인라인 선행 조건 누락 2건)은 문서를 다시 읽어서가 아니라 Live와 Stage를 항목별로 다시 비교하는 과정에서 나왔다.
- 한계: 이 문서에는 인라인 전환 직후 확인 결과를 담지 않았다. 확인 항목 일부가 점검 당시 기록으로 남아 있지 않다.
- 후속 과제: 공용 SG 변경이 외부 연동을 막은 문제([08](./08-shared-sg-change-and-partner-callback-outage.md)), 방화벽 룰그룹의 Stage/Live 분리.
