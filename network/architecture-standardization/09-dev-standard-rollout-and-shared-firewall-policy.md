## 1. 요약
[06. Stage 환경 표준 적용 이후 운영 개선](./06-stage-infra-improvement.md)에서 Stage에 적용한 인프라 표준 5개 항목(배포 흐름 전환, ALB 전용 서브넷 분리, msg/play stateless 최적화, 접근제어 원칙, admin Cloudflare Tunnel 전환)을 Dev에 같은 방식으로 적용했다.
현황 조사 중 Dev와 Stage가 방화벽 규칙 그룹 하나가 아니라 정책 전체를 공유하고 있고, Stage 장애 대응 때 채워 넣은 규칙이 Dev의 정상 트래픽을 차단하고 있음을 발견했다.
방화벽 리소스(`dev`)는 Dev 정책이 아니라 Stage 정책에 연결돼 있었고, Dev 전용으로 만들어 둔 정책은 연결 0개의 고아 리소스였다.
정책과 규칙 그룹을 환경별로 분리하는 작업을 0번(긴급)으로 먼저 처리한 뒤, 5개 항목 중 4개를 완료했고 admin Tunnel 전환은 원인 미확정 이슈로 진행 중이다.

---

## 2. 배경
Stage에서 검증한 표준을 Dev에 옮기는 것은 반복 작업으로 보였다.
그런데 Stage 운영 중 장애 대응으로 방화벽 규칙을 수정한 적이 있었고, 그 수정이 Dev에도 영향을 줬을 수 있었다.
"Stage와 같은 구성"이라고 믿고 시작하면 지금 Dev의 실제 상태를 놓친다.
그래서 적용에 앞서 Dev 방화벽의 현재 상태를 로그와 리소스 연결 관계로 먼저 확인했다.

---

## 3. 담당 역할
- Dev 방화벽의 정책, 규칙 그룹, 방화벽 리소스 연결 관계 조사와 분리
- 5개 표준 항목의 Dev 적용 가이드 작성과 콘솔 실행
- 방화벽 alert 로그와 타겟 헬스로 각 항목의 적용 결과 검증
- Stage에서 배운 설정을 Dev의 비용 제약에 맞게 조정(리전 엔드포인트 처리)

## 4. 진행 과정
### 4.1. 현황 조사에서 공유 오염 발견
> 방화벽 정책이 환경별로 나뉘어 있다고 믿었지만, 실제로는 Dev 방화벽이 Stage 정책에 연결돼 있었다.

처음 문제는 규칙 그룹 하나였다.
Dev 정책과 Stage 정책이 같은 stateless 규칙 그룹을 참조하고 있었다.
Stage 장애 대응 때 이 그룹의 게임 서버 간 통신용 pass 규칙(msg, play 포트)을 Stage의 서브넷 대역으로 채웠고, Dev의 서브넷은 어떤 규칙에도 매치되지 않게 됐다.
Dev alert 로그에서 해당 포트 대상 TCP `blocked` 이벤트로 이 영향을 확인했다.

더 조사하니 문제는 규칙 그룹에서 끝나지 않았다.
Dev 방화벽 리소스 자체가 Dev 정책이 아니라 Stage 정책에 연결돼 있었다.
Dev 전용으로 만들어 둔 정책은 연결 0개로 방치돼 있었다.
규칙 그룹 하나를 고치는 것으로는 부족했고, 정책 전체를 분리해야 같은 사고가 반복되지 않는다고 판단했다.

| 항목 | 발견 당시 | 분리 후 |
| --- | --- | --- |
| 방화벽 리소스(Dev)의 연결 정책 | Stage 정책 | Dev 정책 |
| Dev 정책의 연결 수 | 0 | 1 |
| stateless 규칙 그룹 | Dev/Stage 공유 | 환경별 분리 |
| stateful 규칙 그룹 | Dev 전용이나 이름이 표준과 불일치 | 표준 이름으로 교체 |

### 4.2. 분리 순서 — 영향이 큰 쪽부터, 이름은 교체로 해결
> 이름 변경 API가 없는 리소스는 새로 만들어 교체했고, 분리는 Dev를 먼저 확인하고 Stage는 그 뒤에 했다.

Dev 전용 stateless 규칙 그룹을 새로 만들어 5개 규칙(msg/play 포트 양방향 pass 4개와 나머지 상태 저장 엔진 전달 1개)을 Dev 서브넷 대역으로 채웠다.
stateful(도메인) 규칙 그룹은 이름이 환경 표준과 맞지 않았다.
방화벽 규칙 그룹은 이름을 바꾸는 API가 없어서 표준 이름으로 새로 만들어 교체했고, 도메인 allowlist는 Stage와 같은 40개로 보강했다.
이후 Dev 방화벽의 연결 정책을 Dev 정책으로 바꿨다.
Stage 쪽 stateless 그룹도 같은 방식으로 이름을 정리했다. Dev 분리와 정상 동작을 먼저 확인한 뒤에 진행했다.
검증은 Dev alert 로그에서 msg/play 포트 `blocked` 이벤트가 재발하지 않는지, 도메인 관련 `blocked`가 새로 생기지 않는지로 했다.
Dev에서 새로 필요한 도메인(Stage 목록에 없던 다른 리전 엔드포인트 등)은 이 로그로 확인해 추가했다.

### 4.3. 나머지 표준 항목 — Stage의 방식을 그대로 옮기지 않은 부분
> Dev는 상시 트래픽이 필요 없는 환경이라, 비용이 드는 방식 대신 방화벽 allowlist를 택했다.

배포 흐름 전환과 접근제어 보완은 같은 SG들을 만지는 작업이라 하나로 합쳤다.
SG 하나를 열 때 인바운드와 아웃바운드를 한 번에 끝내기 위해서다. 8개 SG를 정리했다.

ALB 전용 서브넷 분리는 Stage와 같은 방식으로 ALB 4개를 이관했고, 이관 후 타겟 헬스가 전부 healthy인지와 인바운드 라우팅 테이블에 신규 대역이 등록되지 않았는지를 재확인했다.
이 구성은 ALB 트래픽이 방화벽을 거치지 않게 하므로 SG가 유일한 방어선이 된다는 트레이드오프를 문서에 남겼다.
msg NLB는 내부 프로토콜용이라 이관 대상에서 제외했다.

리전 API(sts, autoscaling, ec2) 엔드포인트는 Stage에서 Interface VPC Endpoint로 처리했지만 Dev에서는 방화벽 도메인 allowlist로 처리했다.
Interface Endpoint는 시간당 요금이 붙어서 Dev에는 과하다고 봤다.
이 항목은 원래 계획에서 누락돼 있다가 이후 Dev 배포 파이프라인 복구 중 API 호출이 조용히 타임아웃되는 현상으로 재발견했다.
누락을 발견한 경위와 원인 분석은 별도 보고서로 다룬다.

### 4.4. admin Cloudflare Tunnel 전환 — 설정이 같은데 재현되는 504
> 터널, ALB, SG를 Stage와 대조해 모두 일치했지만, 로그인 콜백 요청만 간헐적으로 504가 났다.

내부 ALB, 커넥터 전용 SG와 인스턴스, 터널, 라우트, 방화벽 규칙까지 모두 만들었고 터널은 Healthy였다.
그런데 관리자 로그인 콜백 경로(실제 로그인 처리)만 504/499가 간헐적으로, 이후 지속적으로 재현됐다.
처음에는 앱 코드 쪽 원인을 의심했다. 로그인 처리에 쓰이는 DB와 캐시를 개별로 호출하면 모두 즉시 응답했고, 실제 유효 토큰으로만 재현돼 코드 경로가 의심스러웠다.

이 가설은 인프라 스택을 위에서 아래로 실측하면서 기각했다.

| 확인 대상 | 결과 |
| --- | --- |
| SG 체인, NACL | Stage와 일치, 커스텀 deny 없음 |
| ALB(양쪽 AZ IP) 직접 호출 | 전부 즉시 응답 |
| 웹 서버와 앱 프로세스(재현 중 실시간 관찰) | 워커 전부 idle. 요청이 인스턴스에 도달하지 않음 |
| 임시 우회 로드밸런서로 직접 접속 | 정상 접속 |

우회 로드밸런서로는 정상이었다는 점이 결정적이었다.
origin 전체 스택이 정상이고, 문제는 Tunnel과 Access 경로 쪽으로 좁혀졌다.
Cloudflare 설정을 Stage의 같은 게임 라우트와 항목별로 대조했지만 라우트, 연결, Access 설정은 사실상 같았다.
다른 점은 이 진단 중 내가 켠 `Disable chunked encoding`(효과가 없어 원복 권장), 커넥터 버전, Access 세션 지속 시간 정도였고 504를 설명하지 못했다.
이 이슈는 원인을 확정하지 못했다. 남은 후보는 해당 호스트에만 걸리는 존 레벨 규칙(WAF, Transform), DNS 레코드, 터널 Live logs로 엣지에서 커넥터까지 요청이 오는지의 확인이다.
그동안은 임시 우회 경로로 급한 작업을 처리한다.

## 5. 성과 및 배운 점
- Dev와 Stage가 방화벽 정책 전체를 공유하던 것을 발견해 환경별로 분리했다. 연결 정책이 어긋난 방화벽 리소스 1개와, 연결 0개이던 고아 정책 1개를 바로잡았다.
- Stage 장애 대응 때 한 수정이 Dev의 정상 트래픽을 차단하고 있었음을 alert 로그로 확인했고, 분리 후 해당 `blocked` 이벤트의 재발 여부를 검증 기준으로 정했다.
- 표준 5개 항목 중 4개(방화벽 분리, SG 정리 8개, ALB 4개 이관, 리전 엔드포인트 allowlist)를 완료했다.
- Stage의 방식을 그대로 옮기지 않고 비용 제약에 맞게 바꿨다. 이 판단은 Dev와 Live가 갈라지는 지점으로 문서에 남겼다.
- 같은 이름의 환경은 같은 구성이 아니다. 공유 리소스는 이름이 아니라 연결 관계를 조회해야 보이고, 환경별 분리는 "처음부터 분리돼 있을 것"이라는 가정이 깨지는 곳에서 찾게 된다.
- 설정 대조는 "차이가 없다"는 결론도 증거가 된다. 504는 설정 차이가 아니라는 것을 확정해 의심 범위를 좁혔지만, 원인은 아직 모른다.
- 후속 과제: admin Tunnel 504 원인 확정과 옛 도메인 정리, Live에는 Interface Endpoint 방식으로 적용([07](./07-live-infra-recheck-and-inline-cutover.md)), Dev 배포 파이프라인 복구 사례의 별도 정리.
