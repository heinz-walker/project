<h1>공용 SG 변경이 외부 연동 수신을 막은 사고 영향 분석</h1>
<i>Impact Analysis of a Shared Security Group Change That Blocked Partner Callbacks</i>
</div>

*2026.09 · 클라우드 네트워크 보안 담당*

---

## 1. 요약
방화벽 인라인 전환 점검 직후, 로드밸런서 두 종류(관리자 화면용, 외부 연동 수신용)가 함께 쓰던 SG에서 인터넷 인바운드(80/443)가 삭제됐다.
그 결과 외부 광고 파트너의 서버 콜백을 받는 ALB 3개로 가는 요청이 51시간 동안 전부 막혔다.
이후 SG 변경 이력과 로그를 조회해, 영향 범위를 CloudTrail, VPC Flow Log, ALB 액세스 로그로 정량화했다.
파트너 6종의 콜백 성공이 차단 구간에 0건이었고, 평소 속도로 환산한 미도달 콜백은 약 2,190건이다.
조치 후 회복은 파트너마다 달랐다. 한 파트너는 재전송으로 약 987건이 회복됐지만 앱이 500으로 거부한 요청이 1,501건 생겼고, 다른 파트너 두 곳은 재전송 흔적이 없었다.
실제 사용자 영향은 차단 구간에 광고 보상을 받지 못한 건이었다. 광고업체 쪽에서는 해당 건이 정상 처리된 것으로 기록돼 있어서, 업체에 누락분을 문의해 받아 사용자 보상을 처리했고 추가 피해 없이 마무리됐다.

---

## 2. 배경
[07. Live 인프라 재조사와 방화벽 인라인 재전환](./07-live-infra-recheck-and-inline-cutover.md)에서 관리자 화면을 인터넷에 직접 노출하지 않고 Cloudflare Tunnel로 전환했다.
이 전환의 마무리로 관리자용 SG에서 `0.0.0.0/0`의 80/443을 삭제하는 것은 의도된 작업이었다.
문제는 이 SG가 관리자 ALB 3개와, 외부 파트너가 콜백을 보내는 ALB 3개의 공용이었다는 점이다.
SG 이름은 "관리자용"이었기 때문에, 이름만 보면 외부 연동과 무관해 보였다.
이 사고는 SG를 지우기 전에 "그 SG를 쓰는 리소스와 최근 인바운드를 먼저 본다"는 절차가 없었던 구조적 문제에서 나왔다.
이 분석은 책임 소재가 아니라 영향 범위와 재발 방지 항목을 확정하기 위해 작성했다.

---

## 3. 담당 역할
- CloudTrail로 차단 시작과 해제 시점, 변경 내역 확정
- VPC Flow Log, ALB 액세스 로그로 영향받은 연동 식별과 영향 규모 추정
- 파트너별 회복 여부 판정과 즉시 확인 항목, 재발 방지 항목 도출
- 근거 로그를 정리한 분석 시트 작성(타임라인, 일별, IP별 집계)

---

## 4. 진행 과정
### 4.1. 무엇이 막혔는지부터 찾기
> 차단된 ALB가 무엇을 받던 주소인지 평소 8일의 ALB 액세스 로그로 먼저 확인했다.

차단 시각은 CloudTrail의 SG 변경 이벤트로 확정했다. 차단 시작은 ALB 이관 약 1시간 뒤이고, 해제는 51.03시간 뒤였다.
다음으로 이 SG를 쓰던 ALB 6개를 분류했다. 관리자 ALB는 사람이 브라우저로 접속하는 곳이고, 나머지 3개는 외부에서 호출하는 곳이었다.
후자의 평소 8일치 ALB 액세스 로그를 요청 경로와 User-Agent로 분류하니 광고 파트너 콜백 6종과 연령 확인 웹 페이지가 나왔다.
파트너 식별은 경로와 User-Agent에서 추정한 것이라 계약과 담당자 확인이 필요하다는 한계를 문서에 남겼다.
80 포트로 온 요청은 전부 스캐너였고 HTTPS 요청만 파트너 호출이어서, 443만 다시 연 조치가 영향이 없다는 것도 같은 로그로 확인했다.

### 4.2. 영향을 숫자로 — 평소 속도와 비교
> ALB 액세스 로그는 ALB에 도달한 요청만 기록하므로, 막힌 구간의 손실은 평소 속도와의 차이로 추정했다.

평소 시간당 성공 건수는 차단 전 190시간의 성공 응답을 기준으로 잡고, 이를 차단 시간에 곱해 "도착했어야 할 콜백"을 계산했다.
파트너 로그가 비는 구간이라 Flow Log의 REJECT 건수를 보조 근거로 썼다. 다만 flow 1건은 연결 1개이지 요청 1건이 아니라서 건수 추정에는 쓰지 않았다.

| 구분 | 평소 일평균 | 차단 구간 예상 | 차단 구간 성공 | 조치 후 초과분 |
| --- | ---: | ---: | ---: | ---: |
| 파트너 A | 866 | 1,842 | 0 | +987 |
| 파트너 B | 90 | 192 | 0 | +5 |
| 파트너 C | 59 | 126 | 0 | +49 |
| 파트너 D | 7 | 14 | 0 | +9 |
| 파트너 E | 4 | 9 | 0 | -5 |
| 파트너 F | 4 | 8 | 0 | +2 |
| 합계 | 1,031 | 2,192 | 0 | +1,047 |

초과분은 조치 후 실제 성공에서 같은 시간의 정상 예상을 뺀 값이고, 양수면 파트너가 재전송한 것으로 추정한다.
회복 양상은 세 갈래로 나뉘었다.
파트너 A는 조치 직후 10분 구간에 평소 대비 50배 넘는 요청이 몰리며 재전송으로 회복됐다.
파트너 B와 E는 재전송 흔적이 없었다. 특히 파트너 E는 조치 후 29시간 동안 0건이었는데, 평소 하루 4건 수준이라 우연일 가능성이 낮아 파트너 쪽 재시도 중단이나 캠페인 종료를 의심했다.
파트너 C는 대부분 회복됐지만 출발 IP 하나가 조치 후 사라지고 새 IP 4개가 나타났다. 파트너가 IP를 바꿔 호출한 것으로 보여 이상 신호인지는 판단하지 않았다.

### 4.3. 회복된 것 안에서도 이상 찾기
> 조치로 요청이 들어오기 시작한 뒤에도 앱이 500으로 응답하고 있었고, 이 건수는 차단 전 8일간 0건이었다.

파트너 A의 회복 구간을 시간별로 보니 앱이 직접 500을 반환한 요청이 1,501건이었다(`target_status_code`도 500이라 앱이 낸 응답이다).
이 500은 조치 직후 몰린 구간에서 끝나지 않고 하루 넘게 이어졌고, 많은 시간대에 해당 파트너 요청의 50–80%가 500이었다.
같은 시간대에 200 응답도 평소와 같은 범위로 나왔다. 새 콜백이 전부 실패한 것은 아니고, 밀린 콜백의 재전송이 앱에서 거부된 모양일 수 있다고 추정했지만 이 로그로는 확정할 수 없다.
요청 URL의 인증값이 모든 요청에서 같아서 같은 콜백의 반복인지도 구분할 수 없었다.
원인 후보(오래된 콜백의 중복·만료 검증, 앱 처리 한계)는 앱 로그를 봐야 가릴 수 있어, 결론에 "원인 불명"으로 남기고 확인 항목에 올렸다.

### 4.4. 보안 영향은 따로 확인
> 차단 구간에 인바운드를 막았다는 사실이 침해가 없었다는 증거는 아니므로, 같은 구간의 외부 트래픽을 별도로 분석했다.

차단 구간에 외부 IP 8,436개가 약 53.9만 flow를 거부당했고, 같은 구간의 통과(ACCEPT) 38건은 시작·종료 시점의 경계 flow여서 실제 통과는 0건이었다.
거부 상위 IP를 분류하니 대부분이 스캐너였고, 하나의 해외 ISP 대역에서 961개 IP가 48만 flow를 보내 가장 컸다. 모두 패킷 1개(40바이트)짜리 연결 시도였다.
이 연결 시도는 443이 다시 열린 뒤에도 약 27.8만 flow가 통과했지만, ALB 액세스 로그에는 이 대역의 요청이 한 건도 없었다. TCP 연결만 시도하고 HTTP 요청까지 가지 못한 것이다.
이 데이터로는 침해 흔적이 보이지 않는다고 결론냈다. 다만 443을 `0.0.0.0/0`으로 열어 두는 한 이 종류의 연결 시도는 계속 닿는다.
앞서 이 차단을 "의도한 결과"로 정리하고 상위 거부 IP를 파트너 가능성으로만 적어 두었던 메모는, 이 분석을 하며 바로잡았다.

### 4.5. 확정과 추정을 분리해 쓰기
> 결론 박스에 "확정한 것"과 "추정한 것"을 따로 적었다.

확정한 것은 차단 시각과 변경 주체, 차단 구간의 성공 0건, 500의 건수와 지속 시간이다.
추정한 것은 파트너 식별, 예상 호출 수, 재전송 회복량, 원인이다.
원인에 대해서는 변경 순서(관리자 ALB를 SG에서 떼어 낸 뒤 443을 다시 연 것)를 근거로 "그 시점에 공용 SG 문제를 인지하고 정리한 것으로 보인다"고만 썼고, 의도는 이 데이터로 확인할 수 없다고 명시했다.
VPC Flow Log의 보존 기간이 30일이라 원본이 곧 사라지므로, 근거 로그는 분석 시트로 정리해 남겼다(쿼리스트링과 최종 사용자 IP는 제외).

### 4.6. 사후 처리 — 업체 기록으로 누락분 복구
> 파트너 서버에는 성공 처리로 남아 있었으므로, 우리 쪽에 없는 건을 업체 기록으로 대조해 받았다.

차단 구간에 사용자가 광고 보상을 받지 못했다는 문의가 들어왔다.
광고업체 입장에서는 사용자의 참여가 정상 처리돼 있었고, 우리 서버로 보낸 콜백만 도달하지 못한 상태였다.
그래서 재전송에만 기대지 않고, 업체에 해당 구간의 처리 내역을 문의해 받아 우리 쪽 지급 기록과 대조했다.
대조로 확인된 누락 건에 대해서는 사용자 보상을 처리했다.
재전송 흔적이 없던 파트너와 앱이 500으로 거부한 건도 같은 방식으로 확인할 수 있었다. 로그만으로는 재전송 여부와 지급 여부를 알 수 없다는 4.5절의 한계를 업체 기록이 메웠다.

## 5. 성과 및 배운 점
- 51시간 차단 구간과 영향받은 연동 6종, 연령 확인 페이지를 로그만으로 식별했고, 미도달 콜백을 약 2,190건으로 추정했다.
- 광고업체 처리 내역으로 누락 건을 대조해 사용자 보상을 처리했고, 이 사고는 추가 피해 없이 마무리됐다.
- 회복된 파트너 안에서도 앱 500 1,501건과, 재전송이 없는 파트너 2곳을 찾아 즉시 확인 항목 4개로 정리했다. 단순히 "조치했으니 정상"으로 닫았다면 보이지 않았을 항목들이다.
- 재발 방지 항목 5개를 제안했다. 외부 연동 전용 SG 분리, SG 규칙 삭제 전 영향 확인 절차(사용 리소스, 최근 7일 ACCEPT 상위 출발지, 해당 출발지의 호출 경로), 콜백 성공률 급감 알람, 파트너 출발 IP 문서화, 대량 연결 시도 감시.
- 공용 SG는 이름이 아니라 부착 리소스를 봐야 한다. 같은 구조가 Stage에도 있었지만 Stage에는 외부 파트너 호출이 없어 문제가 드러나지 않았을 뿐이다.
- 차단 중에는 로그가 비어서 사람이 알아채기 어렵다. 이런 사고는 "있는 로그"가 아니라 "평소 있던 로그가 사라진 것"을 감시해야 보인다.
- 외부 연동은 한쪽 로그만으로 손실을 닫을 수 없다. 우리 쪽 로그에는 "받지 못한 요청"이 남지 않으므로, 상대 시스템의 처리 내역을 받아 대조하는 경로가 복구의 핵심이었다. 평소에 업체별 문의 창구와 처리 내역 조회 방법을 알아 두는 것이 재발 방지 항목에 들어가야 한다.
- 한계: 파트너 식별은 위 분석 시점에는 추정이었다. 분석 수치(예상 호출 수, 회복량)는 평소 속도와의 비교 추정이며, 분석은 조치 후 약 29시간 구간까지만 포함한다. 최종 누락·보상 건수는 이 문서에 포함하지 않았다.
