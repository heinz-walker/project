## 1. 요약
공유 Bastion VPC를 코드화하는 과정에서 Bastion 인스턴스 점검을 요청받았고, 확인 결과 오랫동안 패치가 밀려 있다는 것을 발견했다.
원인은 이 인스턴스가 과거 보안 점검에서 지적됐던 "아웃바운드 전체 허용" 문제를 고친 뒤로 일반 인터넷 경로가 전혀 없는 상태였기 때문이었다.
아웃바운드를 다시 여는 대신, AWS Systems Manager Patch Manager를 도입해 최소 권한 네트워크 구성을 유지하면서 패치를 자동화할 수 있는지 검토하고 실제로 적용했다.
Amazon Linux는 패키지 저장소가 오브젝트 스토리지로 서빙되어 S3 Gateway VPC 엔드포인트만으로 인터넷 아웃바운드 없이 패치가 가능하다는 것을 확인했고, 단일 인스턴스 기준으로 end-to-end 검증까지 완료했다.

---

## 2. 배경
공유 Bastion VPC의 리소스를 OpenTofu state로 편입하는 작업(3번 문서 7절) 중, 이 인스턴스의 상태를 점검해달라는 요청을 받았다.
점검 결과 인스턴스/시스템 상태 체크는 모두 정상이었지만, 패키지 관리자 에이전트 버전이 최신이 아니었고 미패치 보안 업데이트가 상당수 쌓여 있었다.
원인을 짚어보니 네트워크가 외부로 열려 있지 않아 패키지 관리자가 저장소에 접근할 수 없는 상태였다 — 이 아웃바운드 제한은 과거 보안 점검에서 "아웃바운드 전체 허용"이 취약점으로 지적된 뒤 의도적으로 좁혀둔 결과였다.
단순히 아웃바운드를 다시 열면 그 취약점이 재발하므로, 최소 권한 네트워크 구성을 유지한 채로 패치를 자동화할 방법이 필요했다 — 이미 Session Manager로 이 인스턴스를 관리하고 있었으므로, 같은 계열의 AWS Systems Manager 기능인 Patch Manager를 검토 대상으로 삼았다.

---

## 3. 검토 결과 — 적용 가능 여부는 운영체제에 따라 갈린다
Patch Manager와 S3 Gateway VPC 엔드포인트는 표준 EC2 기준으로 추가 비용이 들지 않는다.
다만 "아웃바운드 규칙을 완전히 제거할 수 있는가"는 운영체제에 따라 결론이 달랐다.

| 운영체제 | 패키지 저장소 서빙 방식 | 아웃바운드 완전 제거 가능 여부 |
| --- | --- | --- |
| Amazon Linux | 오브젝트 스토리지(S3) 기반 | 가능 — S3 Gateway 엔드포인트만으로 인터넷 아웃바운드 없이 패치 |
| Windows / Ubuntu | S3 기반이 아님 | 불가 — NAT/인터넷 경로 또는 자체 미러 서버가 여전히 필요 |

즉 이번 발견으로 인터넷 아웃바운드를 완전히 제거할 수 있는 대상은 Amazon Linux 인스턴스로 한정됐다.
Windows/Ubuntu는 패치 자동화·컴플라이언스 가시성 확보 목적으로는 여전히 도입 가치가 있지만, 네트워크 정책(아웃바운드 제거)상의 이득은 없다고 결론지었다 — 이 부분은 별도 장기 과제로 분리했다.

---

## 4. 단계별 적용 계획
전사 자산을 한 번에 다루지 않고, 가장 시급하고 검증된 대상부터 단계적으로 넓히는 계획을 세웠다.

| 단계 | 범위 |
| --- | --- |
| Phase 1 | Bastion 인스턴스(Amazon Linux) 우선 적용 — 패치가 가장 많이 밀려 있고, S3 엔드포인트만으로 완결되는 케이스가 검증된 상태 |
| Phase 2 | 전사 Amazon Linux 자산 조사 결과에 따라 동일 패턴 확대 적용 |
| Phase 3 | Windows/Ubuntu 대응 방안 별도 검토(NAT 경유 아웃바운드 화이트리스트 또는 자체 패치 미러 서버, 장기 과제) |

Phase 1 상세 절차는 다음 순서로 정했다.

1. S3 Gateway VPC 엔드포인트 생성 및 대상 서브넷 라우팅 테이블 연결 확인
2. Patch Baseline 확인·설정(전체 패치 vs 보안 패치만, 자동/수동 승인 규칙 정의)
3. 대상 인스턴스에 Patch Group 태그 부여
4. Maintenance Window 생성(서비스 영향 최소 시간대, Scan/Install 윈도우 분리 여부 결정)
5. Scan 전용 실행으로 선(先) 검증(실제 설치 전에 몇 건이 잡히는지 확인)
6. Install 실행(재부팅 필요 여부 사전 확인, 필요 시 사전 공지)
7. 패치 후 컴플라이언스 확인
8. 기존 보안 그룹 아웃바운드 규칙 재검토(인터넷 관련 규칙이 남아있지 않은지 재확인 및 문서화)

## 5. 사전 점검 — 막혀 있던 지점 2개
실제 적용 전에 네트워크 경로를 점검한 결과, 막혀 있는 지점이 두 곳이었다.

1. S3 Gateway 엔드포인트의 라우팅 테이블 연결 범위가 private 서브넷에만 있고, 대상 인스턴스는 public 서브넷에 위치해 이 엔드포인트를 탈 수 없는 상태였다.
2. 인스턴스에 붙은 보안 그룹의 아웃바운드 규칙에 S3용 443 포트가 없었다 — 내부 통신용 포트 몇 개만 명시적으로 허용돼 있고 그 외에는 전부 제거된 상태였다.

NACL, 라우팅 테이블 변경 범위(대상 서브넷 1개에만 연결돼 다른 리소스에 영향 없음), 엔드포인트 정책, IAM 역할 권한(Patch Manager 실행에 필요한 관리형 정책만 부착돼 있어 과도한 권한 없음), Patch Baseline(Amazon Linux용 AWS 관리형 기본 baseline 존재)은 모두 문제없음을 확인했다.
S3 엔드포인트 정책이 완전 개방 상태라는 점은 별도로 짚어뒀다 — Patch Manager 동작 자체를 막는 문제는 아니지만, 향후 특정 저장소 버킷으로 정책 범위를 좁히는 하드닝 여지로 남겨뒀다.

## 6. 적용 및 검증
막혀 있던 두 지점(엔드포인트 라우팅 연결, 아웃바운드 규칙)을 코드에 반영해 적용했다 — 삭제나 교체 없이 순수 추가만으로 반영됐다.

검증은 네트워크 경로 확인부터 실제 패치 설치까지 단계별로 진행했다.

1. **네트워크 경로 확인**: 인스턴스 세션 안에서 S3 엔드포인트로 직접 요청을 보내 정상 응답을 받는 것을 확인했다.
2. **저장소 접근 확인**: 패키지 관리자의 저장소 메타데이터 갱신 명령이 정상적으로 수신되는 것을 확인했다 — 이 과정에서 약 7개월치 릴리스가 밀려 있었다는 것도 함께 확인됐다.
3. **Scan 실행**: 대상 인스턴스 하나로 범위를 한정해 Scan 전용 명령을 실행, 컴플라이언스 리포트로 미패치 건수를 확인했다 — Scan이 정상적으로 끝났다는 것 자체가 저장소 접근부터 비교·리포트까지 Patch Manager 파이프라인이 문제없이 동작함을 의미했다.
4. **Install 실행**: 동일 인스턴스로 범위를 한정하고, 사용자 재확인 후 실제 설치를 진행했다.

| 항목 | 설치 전 | 설치 후 |
| --- | ---: | ---: |
| 미패치 항목 | 150건대 | 0건 |
| 재부팅 필요 패치 | - | 없음 |
| 실패 건수 | 0건 | 0건 |

인스턴스는 설치 과정 내내 정상 실행 상태를 유지했고, 이 인스턴스 기준으로 패치 컴플라이언스가 100% 완료됐다.
최초 발견 시점의 미패치 건수 추정치와 실제 Scan 결과 사이에는 다소 차이가 있었는데, 이는 발견 시점과 Scan 시점 사이의 자연스러운 차이로 보고 실제 Scan/Install 결과를 최종 기준으로 삼았다.

## 7. 성과 및 배운 점
- "아웃바운드를 다시 열지 않고도 패치를 자동화할 수 있는가"라는 질문에 실제 검증으로 답을 냈다 — Amazon Linux는 가능, Windows/Ubuntu는 별도 방안이 필요하다는 경계를 명확히 했다.
- 네트워크 경로 점검(라우팅 연결, 아웃바운드 규칙)부터 Scan/Install 실행까지 end-to-end로 검증해, 단일 인스턴스 기준으로 미패치 항목을 완전히 해소했다.
- 이관 작업(3번 문서) 중 우연히 발견한 운영 이슈를, 기존 보안 원칙(아웃바운드 최소화)을 훼손하지 않는 해결책으로 연결한 사례다.
- 전사 확대 적용과 Windows/Ubuntu 대응은 별도 단계로 분리해, 검증되지 않은 범위까지 한 번에 넓히지 않도록 했다.
