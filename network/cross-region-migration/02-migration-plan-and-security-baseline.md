## 1. 요약
원본 리전에 있던 Dev 환경 VPC 구성을 대상 리전의 기존 Dev VPC로 이관하는 계획을 수립했다.
대상 리전에는 이미 사내 클라우드 보안 운영 가이드 기준의 3-tier 구조(Firewall/Public/Private)를 갖춘 Dev VPC가 있었으므로, 신규 VPC를 만드는 대신 이 VPC를 그대로 사용하고 기반 리소스를 OpenTofu state로 편입하는 방향으로 정했다.
State는 로컬 파일이 아니라 S3 backend로 관리하고, "리소스 하나를 import할 때마다 plan을 확인하고 의도하지 않은 변경이 없을 때만 다음으로 넘어간다"는 원칙을 세워 실제 실행(3번 문서)의 기준으로 삼았다.
이어서 원본 리전 VPC를 전수 조사해 대상 리전에 아직 없는 리소스(데이터/캐시, 네트워크 엔드포인트, 피어링, 컴퓨트)를 식별하고 우선순위를 매겼다.

---

## 2. 배경
이 이관은 신규 리전에 서비스를 새로 배포하는 프로젝트가 아니라, 이미 운영 중인 Dev 환경의 실제 위치를 원본 리전에서 대상 리전으로 옮기는 작업이었다.
대상 리전에는 별도 목적으로 먼저 구축돼 있던 Dev VPC가 있었기 때문에, "신규 VPC를 만들어 원본 리전 구성을 복제할지" 아니면 "이미 있는 대상 리전 VPC를 그대로 쓰고 부족한 부분만 채울지"부터 결정해야 했다.
후자를 선택한 이유는 두 가지다.
대상 리전 VPC가 이미 사내 보안 기준에 맞는 3-tier 구조를 갖추고 있어 신규로 만들 이유가 없었고, VPC를 새로 만들면 원본 리전과 대상 리전 두 VPC의 구성이 갈라져 이후 어느 쪽이 표준인지 혼란이 생길 수 있었기 때문이다.
이 결정에 따라 계획의 핵심은 "무엇을 새로 만들 것인가"가 아니라 "이미 존재하는 대상 리전 리소스를 어떻게 코드로 편입하고, 원본 리전에만 있는 리소스를 어떻게 골라서 이전할 것인가"로 바뀌었다.

## 3. 준수해야 할 보안 운영 원칙
검토 기준은 사내 클라우드 보안 운영 가이드였다.
이번 이관에서 직접 적용해야 했던 핵심 원칙은 다음과 같다.

| 항목               | 적용 기준                                                                 |
| ---------------- | --------------------------------------------------------------------- |
| VPC              | 계정별 CIDR 영역을 준수하고, 이미 존재하는 대상 리전 VPC를 사용하므로 신규 VPC를 만들지 않는다              |
| Subnet 구조        | Firewall/Public/Private 3-tier 구성을 유지한다                               |
| IAM              | 콘솔 접근은 SSO 계정만 허용한다                                                   |
| Security Group   | Default SG 사용을 금지하고, 내부 통신도 SG-to-SG 기반 접근제어를 사용한다                    |
| SSH              | 기본 22번 포트를 쓰지 않고 별도 비표준 포트를 사용한다                                      |
| Bastion          | 원칙적으로 계정 공용 Bastion을 사용하며, 별도 Bastion이 필요하면 대상 리전에 새로 구축한다            |
| Public Subnet    | ALB와 NAT Gateway가 같은 public subnet에 공존하고, 퍼블릭 IP 자동 할당은 비활성 상태를 유지한다  |
| Private Subnet   | 워크로드 전용으로 사용하고, 기본 egress는 같은 AZ의 NAT Gateway를 사용한다                   |
| Routing          | Public subnet의 egress와 IGW ingress 모두 같은 AZ의 Firewall endpoint를 경유한다  |
| Firewall Logging | FLOW/ALERT 로그를 CloudWatch Logs로 환경별 분리하고, Monitoring Dashboard를 활성화한다 |

이 원칙들은 이후 실제 실행(3번 문서)에서 "원본 리전과 다르게 판단한 지점"의 근거가 됐다.
예를 들어 원본 리전은 S3/DynamoDB Gateway Endpoint를 public route table에도 연결해뒀지만, 대상 리전은 "public subnet의 모든 egress가 같은 AZ Firewall endpoint를 경유해야 한다"는 원칙과 충돌해 private route table에만 연결하기로 결정했다 — 원본 리전이 계정 표준이 정립되기 전의 예외적인 구성이었을 뿐, 대상 리전이 원본 리전을 따라갈 이유는 없다고 판단한 사례다.

## 4. OpenTofu state 관리 방향
State는 로컬 파일이 아니라 S3 backend로 관리하기로 했다.

- 네트워크 작업 디렉터리를 도메인별로 분리해 별도 root module로 둔다.
- S3 backend용 bucket/key/region/profile을 명확히 정의하고, 로컬에는 `.tfstate`를 남기지 않는다.
- `.terraform/`, `*.tfstate`, `*.tfplan`은 버전관리 대상에서 제외하고, provider 버전 재현성을 위한 lock 파일만 커밋한다.
- state가 저장되는 버킷은 versioning을 활성화해, state 자체도 이전 버전으로 복구할 수 있게 한다.

이관 작업 전에 가장 먼저 해야 할 일은 대상 리전에 이미 존재하는 VPC 기반 리소스와 OpenTofu 코드/state를 일치시키는 것이었다.
OpenTofu 관점에서 리소스는 세 가지 상태 중 하나로 나뉜다.

| 상태 | 의미 | 처리 방식 |
| --- | --- | --- |
| AWS에는 있고 state에는 없음 | 기존에 수동으로 만든 리소스 | 코드를 작성한 뒤 import |
| AWS에도 있고 state에도 있음 | 이미 IaC로 관리 중 | plan으로 drift 여부만 확인 |
| 코드에는 있는데 AWS/state에는 없음 | 신규 생성 대상 | plan에 생성으로 표시됨 |

이번 작업의 목표는 기존 대상 리전 VPC 기반 리소스가 plan에서 신규 생성으로 표시되지 않게 만드는 것이었다.
이를 위해 세운 작업 원칙은 다음과 같다.

- 원본 리전 워크로드 리소스부터 작성하지 않고, 먼저 대상 리전 VPC 기반 리소스만 OpenTofu에 편입한다.
- 리소스를 하나 import할 때마다 plan을 확인하고, 의도하지 않은 삭제·교체·변경이 있으면 다음 단계로 넘어가지 않는다.
- 기존 AWS 값과 코드 값이 다르면 우선 코드를 실제 AWS 값에 맞춘다.
- import가 끝나기 전에는 실제 적용을 실행하지 않는다.

## 5. 원본 리전 현황 조사와 이전 후보 우선순위
기반 리소스(VPC/서브넷/라우팅/게이트웨이/방화벽)를 대상 리전 state로 편입한 뒤, 원본 리전 VPC를 전수 조사해 아직 대상 리전에 없는 항목을 식별하고 우선순위를 매겼다.

| 순위 | 대상 | 판단 근거 |
| --- | --- | --- |
| 1 | Dev 계층 데이터/캐시 리소스(NoSQL 테이블, 정적 자산 스토리지, 관계형 DB, 캐시 클러스터) | 애플리케이션이 대상 리전에서 원본 리전 의존 없이 동작하려면 반드시 먼저 채워야 하는 항목 |
| 2 | S3/DynamoDB Gateway Endpoint | 데이터 이관이 끝나야 이 사설 경로가 실제로 유효하게 쓰일 수 있음 |
| 3 | VPC Peering(공유 Bastion VPC) | 조사 결과 다른 환경들도 이미 동일한 패턴으로 이 Bastion VPC와 개별 피어링을 맺고 있어, 환경별 표준 패턴으로 확인됨 |
| 4 | Security Group / EC2 / Application | 애플리케이션 이전 범위, 컴퓨트 전용 모듈 신설 필요 |
| 5 | Network Firewall policy 분리 여부 | 검토 결과 분리하지 않기로 결정(6절 참고) |
| 6 | VPC Flow Logs | 이번 범위에서는 보류 |

1순위 판단에는 데이터 리소스별로 서로 다른 제약이 있었다.

- 관계형 DB(Aurora MySQL)와 캐시(Redis)는 스냅샷 기반 리전 간 이관이 공식 지원 방식이다.
- 캐시 중 Memcached 엔진은 플랫폼 차원에서 스냅샷 기능 자체가 제공되지 않는다 — 데이터 이관이 아니라 빈 클러스터를 새로 만들고 캐시 미스 경로로 다시 채우는 방식으로 접근해야 한다.
- NoSQL 테이블(DynamoDB)은 특정 시점 export/import 방식과, 무중단에 가까운 Global Tables 방식이 있다. Dev 환경은 다운타임 허용 폭이 넓어 export/import를 기본으로 채택했다.
- 정적 자산을 담은 오브젝트 스토리지 버킷은 이름이 전역 네임스페이스 기준으로 유일해야 해서, 원본 리전에 이미 같은 이름의 버킷이 존재하면 대상 리전에 동일 이름으로 즉시 만들 수 없다는 별도 제약이 있었다.

3순위(피어링) 조사 과정에서는 흥미로운 사실도 확인됐다 — 다른 환경(Stage/Live)이 같은 공유 Bastion VPC와 이미 개별 피어링을 맺고 있었다는 것이다.
이 근거로 Dev 환경의 피어링도 원본 리전만의 특수한 구성이 아니라 계정의 환경별 표준 패턴이라고 판단해 대상 리전에도 동일하게 구성하기로 했다.
반면 다른 VPC로 향하는 두 번째 피어링 경로는, 관련 리소스가 향후 정리될 예정이라는 것을 확인하고 대상 리전에 신설하지 않기로 결정했다.

## 6. 원본 리전과 다르게 판단한 항목
원본 리전 구성을 그대로 따라가지 않고, 대상 리전의 현재 표준을 우선한 결정이 몇 가지 있었다.

- **Network Firewall 정책 공유**: 원본 리전은 환경 전용 정책을 썼지만, 대상 리전은 이미 다른 환경과 정책을 공유하는 구조였다. 이 공유가 의도된 설계라는 것을 확인한 뒤, 원본 리전에 맞춰 분리하지 않고 대상 리전의 현재 구조를 유지하기로 했다.
- **Firewall 로그 저장 방식**: 원본 리전은 오브젝트 스토리지로 로그를 보냈지만, 대상 리전은 이미 로그 수집 서비스 기준을 쓰고 있었다. 원본 리전 방식으로 바꾸지 않고 대상 리전 표준을 유지했다.
- **Gateway Endpoint 연결 범위**: 3절에서 설명한 대로, 원본 리전은 public route table에도 연결했지만 대상 리전은 보안 원칙과 충돌해 private에만 연결했다.
- **VPC Flow Logs**: 원본 리전에는 없던 로그였고, 대상 리전에도 이번 범위에서는 신규로 만들지 않기로 결정했다 — 필요해지면 별도로 재검토하기로 남겨뒀다.

이런 판단들은 공통적으로 "원본 리전을 그대로 복제하는 것"이 아니라 "대상 리전에 이미 정립된 표준을 우선하고, 원본 리전이 예외였던 부분은 굳이 따라가지 않는다"는 원칙을 따른 것이다.
