## 1. 요약
2번 문서에서 정한 원칙에 따라, 대상 리전 Dev VPC의 기반 리소스를 OpenTofu state로 편입하고 원본 리전의 데이터·컴퓨트 리소스를 대상 리전으로 옮기는 작업을 실행했다.
네트워크 모듈은 이미 drift 없이 코드와 실제 상태가 일치하는 것을 먼저 확인한 뒤, Gateway Endpoint·VPC Peering을 추가하고 데이터 계층(NoSQL 테이블/정적 자산/관계형 DB/캐시)을 순서대로 이관했다.
이어서 EC2·로드밸런서를 컴퓨트 전용 모듈로 옮기고, 다음 날에는 같은 import 원칙을 공유 Bastion VPC에도 적용해 코드화했다.
이 Bastion VPC 점검 과정에서 인스턴스가 오랫동안 패치되지 않고 있었다는 문제를 발견했는데, 이 내용은 6번 문서에서 별도로 다룬다.

---

## 2. 기반 리소스 재검증과 코드-실물 대조
작업을 시작하기 전, 대상 리전 네트워크 모듈이 실제 AWS 상태와 이미 일치하는지부터 재확인했다.
VPC 설정, 서브넷 6개, 라우팅 테이블 8개(및 라우트), 인터넷 게이트웨이, NAT Gateway 2개, Network Firewall(정책 동기화 상태 포함), 기본 보안 그룹을 AWS CLI로 전수 조회해 코드와 대조했다.
결과는 변경 사항 없음 — 별도 조치 없이 다음 단계로 진행할 수 있는 상태임을 확인했다.

---

## 3. Gateway Endpoint와 VPC Peering
S3/DynamoDB Gateway Endpoint는 2번 문서의 보안 원칙에 따라 private 라우팅 테이블에만 연결하는 코드를 작성해 적용했다.
VPC Peering은 공유 Bastion VPC와의 연결만 신설했다 — 상대 VPC를 조회해보니 이미 다른 환경들이 각자 전용 피어링으로 연결돼 있어 환경별 표준 패턴임을 확인한 뒤 진행했다.
피어링 자체는 같은 계정 안에서 자동 승인으로 즉시 활성화됐지만, 반대편(Bastion VPC 쪽) 라우팅 테이블에는 돌아오는 경로가 없어 편도 통신만 가능한 상태였다 — Bastion VPC의 기존 다른 환경 라우팅 구성을 그대로 참고해 반대편 라우트를 추가한 뒤 양방향 연결을 확인했다.

## 4. 데이터 계층 이관
2번 문서에서 정리한 우선순위에 따라 데이터/캐시 리소스를 이관했다. 리소스 종류별로 방식이 달랐다.

| 리소스 종류 | 방식 | 비고 |
| --- | --- | --- |
| NoSQL 테이블(11개) | 특정 시점 export 후 import | 완료 후 item 단위로 데이터 일치 검증 |
| 캐시(메모리 전용 엔진) | 빈 클러스터 재생성 | 스냅샷 기능 자체가 플랫폼에서 지원되지 않아 재생성 후 캐시 미스 경로로 재적재 |
| 정적 자산 오브젝트 스토리지 | 리전 간 복제 규칙 + 배치 복제 작업 | 이름 충돌로 임시 버킷명 사용, 이후 컷오버 시 정식 이름으로 재정리(5번 문서에서 다룸) |
| 관계형 DB(클러스터 2개) | 스냅샷 생성 → 리전 간 복사 → 복원 | 암호화 키가 리전 종속이라 대상 리전 키를 새로 지정 |
| 캐시(영속성 지원 엔진) | 스냅샷 생성 → 오브젝트 스토리지 경유 → 시딩 | 스냅샷의 리전 간 직접 복사 API가 없어 스토리지를 경유하는 3단계 절차 필요 |

관계형 DB와 캐시(영속성 지원 엔진) 모두 "새 리소스를 만드는 복사"였지 그 자체로 이관 완료를 뜻하지 않았다.
스냅샷 시점 이후 원본에 쓰인 데이터는 새 리소스에 반영되지 않으므로, 애플리케이션이 실제로 새 엔드포인트를 보도록 전환하는 작업이 남아야 진짜 이관이 끝난다 — 이 전환은 애플리케이션/배포 담당 범위라 이 프로젝트 밖으로 남겨뒀다.

캐시 스냅샷의 오브젝트 스토리지 경유 이관에서는 시행착오도 있었다.
처음에는 예전 방식대로 버킷 ACL에 서비스 계정을 추가하는 방법을 시도했으나 권한 오류가 발생했고, 공식 문서를 다시 확인한 결과 현재 권장 방식은 ACL이 아니라 버킷 정책이라는 것을 확인해 재시도 끝에 성공했다.
또한 export한 스냅샷을 원본 리전의 스토리지에서 그대로 참조하려다 "같은 리전의 오브젝트만 시딩에 쓸 수 있다"는 제약에 부딪혀, 대상 리전에 별도 버킷을 만들어 객체를 다시 복사하는 단계가 추가로 필요했다.

## 5. 컴퓨트 전용 모듈 신설과 EC2 이관
EC2는 리전 간 import 대상이 아니라 대상 리전에 새로 생성해야 하는 리소스였다.
AMI를 원본 리전에서 생성해 대상 리전으로 복사한 뒤 그 AMI로 인스턴스를 띄우는 방식을 선택했다 — 이관이 끝나면 복사한 AMI는 정리하는 것을 전제로 했다.

컴퓨트 리소스는 네트워크 모듈의 state를 참조하는 별도 모듈로 신설했다.
7개 인스턴스에 대응하는 보안 그룹을 먼저 만들었는데, 이 그룹들이 서로를 참조하거나 로드밸런서 보안 그룹을 참조하는 구조였다 — 로드밸런서는 아직 이관 전이라, 당장 만들 수 있는 규칙만 채우고 나머지는 로드밸런서 이관 시점에 채우기로 순서를 나눴다.

인스턴스 생성 과정에서 두 가지 실무적인 문제를 만났다.

- 일부 인스턴스 타입이 대상 가용영역에서 지원되지 않는다는 오류가 발생했다 — 같은 서브넷의 다른 인스턴스(신세대 타입)는 문제없이 생성된 것으로 보아 가용영역 자체가 아니라 구세대 인스턴스 패밀리가 해당 영역에서 막힌 것으로 판단했다. 스펙이 거의 동일한 신세대 타입으로 교체해 해결했다.
- 접속용 키 페어가 대상 리전에 없어, 기존 서버에 남아있던 개인키 파일의 핑거프린트를 실제 등록된 키페어와 대조해 동일함을 확인한 뒤 대상 리전에 새로 import했다.

인스턴스 7대가 모두 기동된 뒤 SSH 접속을 확인하는 과정에서, Bastion 인스턴스에 붙은 보안 그룹의 아웃바운드 규칙에 새로 만든 대상 리전 Dev 대역이 빠져 있다는 것도 발견해 규칙을 보완했다.

## 6. 로드밸런서 이관과 정리
컴퓨트 이관 마지막 단계로 로드밸런서 8개를 리스너·타겟그룹·헬스체크·보안 그룹까지 동일한 구성으로 대상 리전에 재작성했다.
이 과정에서 보안 그룹 4개가 서로를 순환 참조하며 plan 단계에서 의존성 순환 오류가 발생했는데, 그중 한 방향의 인바운드 규칙만 별도 리소스로 분리해 순환을 끊는 방식으로 해결했다.

이관에 사용했던 임시 리소스(AMI, DB/캐시 스냅샷, 임시 스토리지 버킷)는 대상 리소스가 실제로 정상 상태에서 복원됐는지 재확인하는 검증 스크립트를 먼저 만들어 dry-run으로 삭제 대상을 확인한 뒤 실행했다.
모든 검증이 "복원 완료" 상태일 때만 삭제하도록 안전장치를 넣었고, 삭제 후 재조회로 이관 원본이나 다른 환경의 리소스에는 영향이 없음을 확인했다.

## 7. 공유 Bastion VPC 코드화
컴퓨트 이관을 마친 다음 날, 같은 import 원칙을 공유 Bastion VPC에도 적용했다.
State 버킷 구조도 이 시점에 재검토했다 — 처음에는 기존 Dev 전용 버킷에 key만 추가하면 된다고 판단했으나, 다른 환경도 곧 같은 방식으로 코드화될 예정이라는 것을 확인하면서 버킷을 계정 단위로 통합하고 환경별 key prefix로 구분하는 구조로 재설계했다.
기존 3개 모듈(네트워크/컴퓨트/데이터)도 이 새 버킷 구조로 함께 마이그레이션했다.

Bastion VPC는 20여 개 리소스를 한 번에 import한 뒤 plan을 확인했는데, 처음에는 7개 항목에서 의도치 않은 diff가 나왔다.

| 문제 | 원인 |
| --- | --- |
| 기본 보안 그룹의 태그가 삭제될 예정으로 표시됨 | 코드에 태그·삭제 옵션이 누락돼 있었음 |
| 보안 그룹 아웃바운드 규칙 하나가 제거될 예정으로 표시됨 | 인라인 규칙 일부와 별도 관리 규칙이 같은 방향에서 이중으로 선언돼 충돌 |
| 여러 리소스의 이름 태그가 코드와 실제가 불일치 | 리소스 태그에 남아있던 오타가 아직 정정되지 않음 |

보안 그룹은 인라인 규칙과 별도 리소스 규칙을 섞으면 그 방향 전체가 authoritative로 취급돼 충돌이 난다는 것을 확인하고, 해당 방향 전체를 별도 리소스로 통일해 해결했다.
나머지는 누락된 옵션을 코드에 채우고 실제 리소스의 태그 오타를 일괄 정정해, 최종적으로 전체 리소스가 plan 변경 없음 상태로 코드 관리 대상이 됐다.

이 Bastion 인스턴스 점검 과정에서 패치 상태를 확인해달라는 요청이 있었고, 오랫동안 패치가 밀려 있었다는 사실을 발견했다 — 이 발견과 후속 조치는 6번 문서에서 별도로 다룬다.
