## 1. 요약
4번 문서의 Auto Scaling Group 전환 직후, 앱 7개 중 3개의 로드밸런서 헬스체크가 계속 실패했다.
인스턴스에 직접 접속해 로그와 설정 파일을 확인하는 읽기 우선 조사를 진행했고, 두 가지 근본 원인을 찾아 그중 인프라 경계 안에 있는 부분은 직접 조치했다.
나머지 4개 앱도 같은 방식으로 읽기 전용 점검을 진행해, 겉보기에는 healthy였지만 실제로는 특정 기능에서 런타임 오류가 반복되고 있던 사례와, 애초에 부팅 시 서비스 프로세스를 띄우는 경로 자체가 없던 사례를 추가로 발견했다.
설정값 교체로 해결 가능한 항목은 직접 수정하고, 애플리케이션 코드/배포 정책 판단이 필요한 항목은 담당 팀에 넘겼다.

---

## 2. 조사 경로
운영 콘솔이나 SSH가 직접 열려 있지 않은 환경이라, Bastion을 경유하는 다단계 SSH 경로로 각 인스턴스에 접속했다.
정확한 홉 구성과 계정명은 이 문서에 남기지 않으며, 모든 조사는 파일 변경이나 프로세스 재시작 없이 로그 확인·설정 파일 열람·프로세스 상태 조회 등 읽기 전용 명령으로만 진행했다(실제 수정이 필요했던 항목은 별도로 명시).
일부 인스턴스는 이후 시점에 원격 명령 실행 서비스에 등록된 것이 확인되어, 다단계 SSH 대신 비대화형 명령 실행으로 조사를 이어가기도 했다.

---

## 3. 근본 원인 A — 누락된 인스턴스 태그로 인한 설정 경로 오염
헬스체크가 실패한 3개 앱의 기동 스크립트는 인스턴스 메타데이터(IMDS)에서 대문자로 된 환경 구분 태그를 읽어 설정 파일 경로를 구성하는 구조였다.
그런데 Auto Scaling Group에는 소문자 버전의 환경 태그만 있고, 스크립트가 실제로 참조하는 대문자 태그는 없었다.

- 태그가 없어 IMDS가 404를 반환했고, 애플리케이션이 이 **404 응답의 HTML 본문 전체를 파일 경로 문자열에 그대로 이어붙여** 존재하지 않는 경로를 열려다 오류로 죽는 것을 로그에서 직접 확인했다.
- 조치는 Auto Scaling Group 태그에 누락된 대문자 환경 태그를 추가하는 것으로 끝났다 — 이미 떠 있던 인스턴스에는 태그를 직접 추가해 즉시 검증했다.
- 태그 추가 후 재기동하자 설정 파일을 정상적으로 찾아 다음 단계로 넘어가는 것을 확인했다 — 이 문제 자체는 해결됐다.

---

## 4. 근본 원인 B — 인프라는 이전됐지만 앱 설정이 옛 리전을 가리킴
태그 문제를 해결한 뒤에도 한 앱이 캐시 연결 단계에서 계속 죽었다.
설정 파일을 열어보니 캐시 클러스터 엔드포인트가 옛 리전(원본 리전) 주소 그대로 박혀 있었다.

인프라 계층의 캐시 클러스터는 이미 3번 문서에서 대상 리전에 정상적으로 이관돼 있었다 — 문제는 **배포된 애플리케이션 아티팩트(설정 파일)의 값만 옛 리전 시절 그대로 남아있는 것**이었다.
이 설정 파일은 별도 배포 저장소에서 관리되는 애플리케이션 아티팩트로, 이 프로젝트(OpenTofu 인프라 저장소)의 관리 범위 밖이었다.

인프라와 애플리케이션 배포 경계를 명확히 구분한 뒤, 설정 파일의 리전/엔드포인트 값을 대상 리전 기준으로 수정하고 재배포하는 작업은 애플리케이션 배포 담당으로 처리(직접 수정 후 배포 저장소에 반영)했고, 캐시 연결이 정상화되며 해당 앱의 헬스체크가 healthy로 전환됐다.

같은 방식으로 나머지 2개 앱의 설정 파일도 확인한 결과, 하나는 옛 리전용 설정 파일이 아예 존재하지 않아 다른 환경의 설정을 템플릿 삼아 새로 작성해야 했다.
두 앱 모두 캐시/내부 로드밸런서 엔드포인트를 대상 리전 값으로 채운 뒤 재기동해, 3개 앱 전부 타겟그룹 헬스체크가 healthy로 전환된 것을 확인했다.

## 5. 부가 발견 — 설정값 불일치로 조용히 저하된 기능
한 앱의 설정에는 소속 Auto Scaling Group 이름을 가리키는 값이 있었는데, 이 값이 옛 리전 시절 이름 그대로 남아 대상 리전의 실제 그룹 이름과 달랐다.
애플리케이션 코드를 직접 확인한 결과 이 값은 단순 로그용이 아니라, 같은 그룹 내 다른 정상 인스턴스 목록을 조회하는 API 호출에 실제로 쓰이는 파라미터였다.

값이 틀려도 API 자체는 오류 없이 빈 목록을 반환하도록 설계돼 있어 크래시나 헬스체크 실패로는 이어지지 않았다 — 대신 여러 인스턴스가 서로를 인식해야 하는 피어 탐지 기능이 조용히 무력화돼 있었다.
Dev 환경은 인스턴스가 1대뿐이라 체감 문제가 없었을 뿐, 잠재적 결함이었다.
다른 환경의 같은 설정은 이미 올바른 값으로 갱신돼 있었던 것으로 보아, 이번 리전 이관 때만 놓친 값으로 판단해 대상 리전 실제 그룹 이름으로 수정했다.

## 6. 나머지 2개 앱 — 읽기 전용 점검
헬스체크 실패 목록에는 없었지만, 같은 유형의 문제가 조용히 남아있을 수 있어 나머지 2개(게임 서버 2종)도 동일한 방식으로 점검했다.

### 6.1. 게임 서버 A(PHP 기반 웹 레이어)
설정 파일 대부분이 옛 리전 값 그대로였다 — 관계형 DB 엔드포인트, 캐시 클러스터, 정적 자산 URL, 내부 로드밸런서, 리전 코드 등 광범위하게 남아있었다.
겉보기에는 웹 레이어(nginx/PHP)가 정상 기동 중이라 타겟그룹은 계속 healthy였지만, 오류 로그를 확인한 결과 특정 캐시 연결 함수에서 타임아웃 예외가 반복적으로 발생하고 있었다 — 헬스체크가 보는 경로와 실제 장애가 나는 경로가 달라, healthy 상태 뒤에 실패가 숨어 있던 사례다.
대상 리전에 대응 리소스가 실제로 존재하는지 하나씩 확인한 뒤, 대응 리소스가 있는 값은 대상 리전 기준으로 교체했다.
반면 대응 리소스가 없거나 다른 계정 소유로 확인된 일부 값(분석 로그 스트림, 쿼리 결과 저장소 등)은 이미 죽은 경로이거나 접근 권한이 없는 리소스라 손대지 않고 애플리케이션 팀 확인 대상으로 남겼다.
같은 인스턴스에는 부가 게임 콘텐츠를 관리하는 프로세스 관리자가 설치돼 있었지만 관리 대상 프로세스가 0개였다 — 이후 애플리케이션 팀에 확인한 결과 실제로 사용하지 않는 콘텐츠로 확인되어 결함이 아닌 것으로 종료했다.

### 6.2. 게임 서버 B(실시간 로직 포함)
IMDS 커스텀 태그가 전혀 없는 것은 다른 앱들과 같았고, 설정 파일에도 같은 유형의 옛 리전 값(캐시, 내부 로드밸런서, 리전 코드)이 남아있어 대상 리전 값으로 교체했다.

다만 이 앱은 설정 문제보다 더 근본적인 문제가 있었다 — **부팅 시 서비스 프로세스를 띄우는 경로 자체가 존재하지 않았다.**
프로세스 목록을 확인한 결과 관련 프로세스가 전혀 없었고, 리스닝 포트도 서비스가 열어야 할 포트들이 하나도 열려 있지 않았다.
원인을 추적한 결과, OS 부팅 스크립트는 로그만 남기는 빈 스텁이었고, 별도의 배포 스크립트는 이미 사용되지 않는 것으로 보이는 과거 배포 서버에 의존하고 있어 실행돼도 곧바로 실패하는 구조였다.
예약 작업(cron)도 등록돼 있지 않아 정기적으로 재기동을 시도하는 경로도 없었다.

이 문제는 설정값 교체로 해결되지 않는, 배포 방식 자체를 다시 설계해야 하는 사안이라 이번 프로젝트 범위 밖으로 두고 애플리케이션 배포 담당에 넘겼다.
후속 확인 결과, 이 앱은 Dev 환경에서 계속 운영해야 하는 것으로 확정됐고, 실제 실행 방법은 별도 기동 스크립트를 직접 실행하는 방식이라는 답변을 받았다 — 부팅 시 이 스크립트를 자동으로 실행시키는 트리거(예: 인스턴스 부팅 스크립트 또는 서비스 유닛)를 다시 만드는 작업이 후속 과제로 남았다.

## 7. 종합
7개 앱 전체 조사 결과를 정리하면 다음과 같다.

| 항목 | 결과 |
| --- | --- |
| 근본 원인 A(누락 태그 → 설정 경로 오염) | 해결 완료 — 태그 추가 |
| 근본 원인 B(앱 설정의 옛 리전 캐시 엔드포인트) | 해결 완료 — 설정 교체 및 재배포(인프라 밖, 배포 담당 처리) |
| 설정값 불일치로 인한 기능 저하(피어 탐지) | 해결 완료 — 설정 교체 |
| 게임 서버 A의 잔존 옛 리전 값 | 부분 해결 — 대응 리소스가 있는 값은 교체, 없거나 타 계정 소유인 값은 애플리케이션 팀 확인 대기 |
| 게임 서버 A의 캐시 타임아웃 | 원인 확인(엔드포인트 교체로 해소 예상), 재검증은 애플리케이션 팀 몫 |
| 게임 서버 B의 잔존 옛 리전 값 | 해결 완료 — 설정 교체 |
| 게임 서버 B의 부팅 시 프로세스 미기동 | 범위 밖 — 배포 방식 재설계 필요, 애플리케이션 배포 담당에 인계 |

이번 조사에서는 헬스체크가 잡아내는 것(엔드포인트 응답 여부)과 실제 장애(특정 기능 경로의 예외, 조용히 무력화된 기능, 아예 기동되지 않는 프로세스)가 서로 다를 수 있다는 것을 여러 사례로 확인했다.
인프라 이관이 끝났다고 해서 애플리케이션 계층까지 자동으로 따라오지 않는다는 점, 그리고 그 경계를 명확히 구분해 인프라 범위 안에서 해결 가능한 것과 애플리케이션 팀에 넘겨야 하는 것을 나누는 판단이 필요했다.
