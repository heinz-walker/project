## 1. 요약
3번 문서에서 "완료"로 정리했던 EC2 이관을 재점검한 결과, 실제로는 원본 리전의 Auto Scaling Group 구성이 전혀 반영되지 않고 고정 인스턴스 7대로만 옮겨진 상태였다는 것을 확인했다 — 직접 발견한 게 아니라 사용자의 지적으로 다시 들여다본 결과였다.
원본 리전을 다시 조사해 실제로는 6개의 Auto Scaling Group이 있었다는 것을 확인했고, 그중 하나는 가동 대수가 0이라 최초 조사(실행 중인 인스턴스 기준 스냅샷) 때 아예 누락됐던 것도 새로 발견했다.
Auto Scaling Group 기반으로 전환하는 과정에서, 이관 때 만들었던 AMI 7개가 이미 정리 스크립트로 삭제됐다는 사실도 함께 확인했다 — 추측이 아니라 정리 스크립트 내용과 실제 조회 결과를 대조해 확정했다.
AMI를 다시 확보하고, 자동 인스턴스 타입 선택 방식이 일으키던 반복 실패까지 고정 타입으로 바꿔 해결한 뒤 Auto Scaling Group 전환을 완료했다.

---

## 2. 재점검 배경
컴퓨트 모듈은 앱 7개를 전부 단일 EC2 인스턴스 리소스로 정의하고 있었다.
그런데 원본 리전 인스턴스 이름 중 5개에는 자동화 여부를 뜻하는 표기가 붙어 있었고, 애초 이관 계획서에도 "이 표기가 붙은 인스턴스는 기존 배포/생성 자동화 여부를 먼저 확인한다"는 항목이 이미 있었다.
하지만 실제 작업 기록을 다시 살펴보니 이 확인이 실행된 흔적이 없었고, 그 표기는 인스턴스의 이름에만 그대로 남은 채 가용영역·타입·보안 그룹만 조사된 상태로 고정 인스턴스로 이관돼 있었다.
계획 단계에서 이미 짚어뒀던 확인 항목이 실행 단계에서 누락된 사례였다.

---

## 3. 원본 리전 Auto Scaling Group 현황 재조사
원본 리전을 AWS CLI로 다시 조회한 결과, 대상 리전으로 옮겨진 7개 앱 중 5개가 실제로는 Auto Scaling Group으로 운영되고 있었다.

| 구분 | Auto Scaling Group 존재 여부 |
| --- | --- |
| 앱 5종(게이트웨이·메시지 처리·라우팅·게임 서버 2종) | 있음 — 최소/희망/최대 용량 설정, 특정 앱은 최대 10대까지 확장 가능 |
| 관리 서버 1종 | 없음 — 원본 리전에서도 단일 EC2였음(이관 판단은 맞았음) |
| CI/CD 러너 인스턴스 | 없음 — 원본 리전에서도 단일 EC2였음(이관 판단은 맞았음) |

6개 Auto Scaling Group 모두 현재 최소/희망 용량이 0이고 스케일링 정책이나 예약된 작업이 전혀 없었다 — CloudWatch 알람 기반 자동 확장이 아니라, 희망 용량을 수동 또는 외부 프로세스로 0과 1 사이에서 토글하는 운영 방식으로 보였다.

가장 중요한 발견은 **최초 조사에서 아예 존재를 놓쳤던 Auto Scaling Group 하나**였다.
게임 서버 계열 앱 하나가 같은 구성을 공유하는 두 번째 Auto Scaling Group을 갖고 있었는데, 이 그룹은 희망 용량이 0이라 "현재 실행 중인 인스턴스" 기준으로 스냅샷을 떴던 최초 조사(3번 문서 5절)에는 잡히지 않았다.
대상 리전에는 이 그룹에 대응하는 리소스 자체가 없었다 — 계획 문서도 이 존재를 놓쳤던 것이다.

컴퓨트 모듈이 실제로 만들어낸 구조는 Auto Scaling Group 없이 "정확히 1대만 항상 떠 있는" 구조였고, 로드밸런서의 타겟그룹도 인스턴스 ID를 코드에 직접 고정하는 방식으로 연결돼 있었다 — 트래픽이 늘어도 자동으로 인스턴스가 늘어나는 구조가 아니었다.

## 4. Auto Scaling Group 전환과 AMI 삭제 발견
Auto Scaling Group 전환 여부, 새로 발견된 그룹의 반영 여부, 용량 값을 원본 리전 그대로 가져갈지 등 여러 결정 사항을 정리한 뒤, 실제 전환 작업에 들어갔다.

전환을 위해 Launch Template에 넣을 AMI를 다시 확보하려다, **이관 때 만들었던 대상 리전 복사본 AMI 7개가 이미 존재하지 않는다**는 것을 발견했다.
원본 리전과 대상 리전 복사본 양쪽 모두 조회 결과가 빈 배열로 나왔다 — 원인은 추측이 아니라 확인된 사실이었다.
이관 직후 실행했던 정리 스크립트가 "인스턴스가 이미 이 AMI들로 기동을 마쳤으니 이관 완료 후 정리 대상"이라는 주석과 함께 원본 리전 7개, 대상 리전 복사본 7개를 합쳐 총 14개를 정리하도록 작성돼 있었던 것이다.
이 스크립트는 AMI 삭제와 함께 연결된 백업 스냅샷까지 같이 지우도록 만들어져 있어, 스냅샷에서 AMI를 복구하는 것도 불가능했다.

다행히 현재 실행 중인 대상 리전 인스턴스 7대에는 영향이 없었다 — EBS 기반 인스턴스는 부팅 이후 원본 AMI를 다시 참조하지 않기 때문이다.
하지만 이 AMI ID로는 더 이상 새 인스턴스를 띄울 수 없는 상태였고, Auto Scaling Group으로 전환하려면 어차피 Launch Template에 새 AMI가 필요했으므로 이 문제를 먼저 해결해야 했다.

AMI를 다시 뜨는 방법은 두 가지였다 — 현재 대상 리전에서 실행 중인 인스턴스에서 새로 뜨는 방법과, 원본 리전 Launch Template이 참조하는 원본 AMI를 다시 복사하는 방법이다.
전자는 이관 이후 반영된 최신 상태를 그대로 가져갈 수 있다는 장점이 있었지만, 최종적으로는 후자를 선택했다 — 원본 리전 이미지 쪽이 향후 재현성 측면에서 더 명확한 기준점이 된다고 판단했기 때문이다.
공유 Launch Template을 쓰는 앱 3종은 한 번만 복사해 같은 대상 리전 AMI를 함께 참조하도록 정리했다.

## 5. 자동 인스턴스 타입 선택이 일으킨 반복 실패
Auto Scaling Group 2개(메시지 처리, 라우팅)는 특정 인스턴스 타입을 고정하는 대신 vCPU/메모리 범위로 AWS가 자동으로 타입을 고르는 방식(속성 기반 선택)을 쓰고 있었다.
이 방식이 최저가 우선 전략과 결합되면서, 넓은 범위 조건에 맞는 구세대 인스턴스 패밀리가 계속 선정되고 있었다.
문제는 로드밸런서(네트워크 로드밸런서, 타겟 타입이 인스턴스)가 이 구세대 패밀리를 타겟으로 등록할 수 없어, 인스턴스가 뜨자마자 등록 실패 → 종료 → 재시도가 반복되는 launch-fail 루프가 발생하고 있었다는 것이다.
실제 활동 이력을 조회한 결과 한쪽은 하루 반 동안 100건 넘게, 다른 한쪽은 5건이 반복된 뒤 멈춘 상태였다.

이 두 그룹은 이미 이전 단계(3번 문서)에서 고정 인스턴스로 이관할 때 같은 이유로 신세대 타입으로 바꾼 전례가 있었다.
같은 판단을 Auto Scaling Group 전환에도 그대로 적용해, 자동 선택 방식을 가져오지 않고 이미 쓰고 있던 고정 타입을 유지하기로 했다.

---

## 6. 전환 완료
아래 결정을 반영해 컴퓨트 모듈을 다시 작성했다.

- 최소/최대 용량은 원본 리전 값을 그대로 가져왔다.
- 희망 용량은 원본 리전 조사 시점 기준 0이었지만, 그대로 가져오면 대상 리전에서 계속 떠 있던 인스턴스가 적용 직후 전부 꺼지는 문제가 생겨 1로 설정했다.
- 최초 조사에서 새로 발견된 그룹은 실제 트래픽 서빙 여부가 불분명해 이번 전환에서는 제외하고 별도 확인 후 진행하기로 했다.
- 자동 인스턴스 타입 선택 방식은 가져오지 않고 고정 타입을 유지했다.

고정 인스턴스 5개를 삭제하고 Launch Template과 Auto Scaling Group 5개, 그에 맞춘 타겟그룹 연결 방식으로 교체하는 변경을 적용했다.
plan 결과 생성 10개(Launch Template 5 + Auto Scaling Group 5), 삭제 11개(고정 인스턴스 5 + 기존 타겟그룹 연결 6) 외에 다른 변경은 없음을 확인한 뒤 적용을 완료했다.

## 7. 성과 및 배운 점
- "완료"로 표시된 작업이라도 원본 환경의 구성 방식(이 경우 Auto Scaling Group 여부)까지 재현됐는지는 별도로 검증해야 한다는 것을 실제 사례로 확인했다 — 계획 단계의 확인 항목이 실행 단계에서 누락되는 일이 실제로 일어난다.
- 정리 스크립트가 남긴 자원 상태 변화(AMI 삭제)를 "그럴 것이다"로 추정하지 않고, 스크립트 원문과 실제 조회 결과를 대조해 사실로 확정한 뒤에 복구 계획을 세웠다.
- 자동 인스턴스 타입 선택처럼 편리해 보이는 설정이 실제로는 특정 리소스(로드밸런서 타겟 타입)와 충돌할 수 있다는 것을 반복 실패 로그로 직접 확인하고, 이전 단계의 유사 사례(3번 문서의 타입 고정 전례)를 근거로 일관된 해결책을 적용했다.
- 가장 리스크가 큰 변경(고정 인스턴스 삭제 + 신규 리소스 생성)에 들어가기 전, plan으로 생성/삭제 개수를 정확히 확인하고 의도한 리소스 외에는 변경이 없음을 검증하는 절차를 지켰다.
