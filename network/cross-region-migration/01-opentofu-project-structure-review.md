## 1. 요약
리전 간 이관을 실행하기 전, 기존 OpenTofu 코드 구조(도메인별 디렉터리 분리, 도메인마다 독립 state)를 그대로 유지할지 다른 구조로 바꿀지부터 검토했다.
단일 state 구조, 루트 모듈이 하위 모듈을 조합하는 구조 등 대안 3가지를 포함해 총 4가지 구조를 일곱 개 기준으로 비교했다.
실제 코드의 리소스 개수(도메인 합계 약 140개)를 기준으로 실행 속도를 따져본 결과, 구조 선택이 성능 문제가 아니라 state 격리·독립 적용·탐색성 문제라는 결론을 내렸다.
현재 구조를 유지하되 오케스트레이션 수준의 최소 보완만 추가하기로 했고, 향후 다른 리전/환경으로 반복 배포해야 하는 시점을 대비한 공통 모듈 확장안도 함께 정리했다.

---

## 2. 배경
이관 작업에 들어가기 전, 기존 코드가 `network`/`database`/`compute` 세 도메인으로 나뉘고 도메인마다 독립된 backend(state)를 쓰는 구조라는 것을 먼저 확인했다.
이 구조를 그대로 가져갈지, 아니면 이관을 계기로 단일 state로 단순화하거나 재사용 가능한 모듈 구조로 바꿀지 판단이 필요했다.
이 프로젝트가 끝나면 같은 구성을 다른 리전/환경에도 반복 적용해야 할 가능성이 있었기 때문에, 구조를 먼저 정리해두지 않으면 이후 실제 이관 작업(3–4번 문서)에서 코드 배치 방식이 흔들릴 수 있다고 판단했다.

---

## 3. 비교 대상 구조
현재 구조를 포함해 4가지 구조를 비교 대상으로 삼았다.

| 구조 | 설명 |
| --- | --- |
| 1. 도메인별 독립 state (현재) | 도메인별 경로 분리, 경로마다 독립 backend/state, `terraform_remote_state`로 상호 참조 |
| 2. 단일 경로·단일 state | 하나의 경로에 전체 리소스 정의, 단일 state |
| 3-a. 루트 모듈 조합·단일 state | 경로는 분리하되 상위 루트에서 `module` 블록으로 실제 조합, backend는 루트 하나 |
| 3-b. 독립 state + 오케스트레이션 | 경로·state는 구조 1과 동일하게 유지하되, 적용 순서를 README/Makefile 등으로 명시 |

구조 3은 상위 root가 하위 경로를 Terraform `module` 블록으로 실제로 호출하는지 여부에 따라 3-a와 3-b로 갈린다.
3-a는 backend가 root module 기준으로 결정되는 OpenTofu의 특성상 child module이 독립 state를 가질 수 없어 state가 통합되고, 3-b는 오케스트레이션 도구가 실행 순서만 안내할 뿐 state는 그대로 분리 유지된다.

## 4. 평가 기준과 비교 결과
구조를 같은 관점에서 비교하기 위해 아래 일곱 기준을 사용했다.

| 평가 기준 | 의미 |
| --- | --- |
| State 격리·변경 영향 범위 | 한 작업의 state 오류나 의도치 않은 변경이 다른 도메인에 미치는 직접 영향 범위 |
| 독립 적용 가능성 | 다른 도메인과 별개로 plan·승인·apply할 수 있는 정도 |
| 의존성 명시성 | 도메인 간 데이터 흐름과 적용 순서가 코드·도구에서 드러나는 정도 |
| 동시 작업성 | 서로 다른 담당자가 동시에 plan/apply할 때 lock 대기·stale plan이 생길 가능성 |
| 코드 재사용성 | 같은 구성을 다른 환경에서 중복 없이 사용할 수 있는 정도 |
| 탐색성 | 새 참여자가 전체 구성과 변경 위치를 파악하기 쉬운 정도 |
| 운영·전환 비용 | backend·권한·실행 도구의 관리 부담과 현재 구조에서 옮길 때의 비용 |

| 구조 | State 격리 | 독립 적용 | 의존성 명시성 | 동시 작업성 | 재사용성 | 탐색성 | 운영·전환 비용 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1. 도메인별 독립 state (현재) | 높음 | 높음 | 낮음–중간 | 높음 | 낮음 | 중간 | 운영 중간 / 전환 없음 |
| 2. 단일 경로·단일 state | 낮음 | 낮음 | 높음 | 낮음 | 낮음 | 높음 | 운영 낮음 / 전환 중간 |
| 3-a. 루트 모듈 조합·단일 state | 낮음 | 낮음 | 높음 | 낮음 | 높음 | 높음 | 운영 중간 / 전환 높음 |
| 3-b. 독립 state + 오케스트레이션 | 높음 | 높음 | 높음 | 높음 | 낮음 | 높음 | 운영 중간–높음 / 전환 낮음 |

구조 1은 현재 필요한 격리와 독립 적용에는 강하지만, remote-state output을 통한 의존성 계약과 여러 디렉터리 탐색을 사람이 관리해야 한다.
구조 2는 가장 단순하지만 독립 배포가 잦아지면 하나의 lock과 큰 변경 영향 범위가 비용으로 바뀐다.
구조 3-a는 재사용성과 의존성 표현에는 강하지만 state 관점에서는 구조 2와 같은 단일 root 제약을 가진다.
구조 3-b는 구조 1의 state 분리를 유지한 채 의존성 명시성과 탐색성만 보완하는 절충안이다.

## 5. 실행 속도(성능) 비교
plan/apply 소요 시간을 결정하는 요인은 state 파싱이나 그래프 계산이 아니라 리소스별 AWS API 호출(refresh) 비용이다.
따라서 실행 시간은 "state가 몇 개로 나뉘어 있는가"가 아니라 "한 번의 명령이 처리하는 리소스 개수"로 결정된다.

실제 코드의 `resource` 블록을 직접 센 결과는 다음과 같다.

| 도메인 | 리소스 개수 | 주요 구성 |
| --- | ---: | --- |
| network | 46개 | route/route table/subnet/NAT/EIP/VPC/IGW/peering/firewall 등 |
| database | 27개 | DynamoDB 11, Security Group 3, RDS 클러스터(+인스턴스) 4, ElastiCache 관련 4 등 |
| compute | 67개 | ALB 리스너 17, Security Group 14, LB 8, Target Group(+attachment) 16, EC2 인스턴스 7 등 |
| 세 도메인 합계 | 140개 | — |

도메인 하나만 plan/apply할 때 refresh 대상은 27–67개 수준이라 기본 병렬도(10)로도 대개 수 초에서 십수 초 안에 끝난다.
세 도메인을 전부 하나의 state로 합쳐도 총 140개 수준이라 refresh 시간은 도메인 1–2개를 처리하는 시간의 2–3배 정도에 머문다.
이 규모에서는 통합 state와 분리 state 사이의 실행 속도 차이가 운영에 지장을 줄 만큼 크지 않다는 결론을 내렸다.
다만 리소스 총합이 수백–수천 개로 늘거나, 특정 리소스 타입에서 API rate limit이 발생하거나, CI에서 plan을 PR마다 반복 실행하는 경우에는 성능도 실질적 근거로 바뀔 수 있다는 점은 별도로 남겨뒀다.

## 6. 결론 및 권장 사항
State 분리는 조직 규모나 리소스 종류만으로 결정할 규칙이 아니라, 누가·얼마나 자주·어떤 승인 단위로 변경을 적용하는지와 장애가 났을 때 함께 감수할 수 있는 변경 범위로 판단해야 한다는 원칙을 먼저 세웠다.
이 프로젝트는 이미 도메인별로 승인·적용 시점이 다른 이관 작업(데이터 이관은 별도 승인, 네트워크 변경은 별도 승인)이 진행 중이었으므로, 구조 1(현재)을 유지하는 것이 맞다고 판단했다.

대신 구조를 바꾸지 않고도 구조 3-b 수준의 효과를 얻을 수 있는 최소 보완만 추가하기로 했다.

- 최상위 문서에 도메인 간 적용 순서(예: 네트워크 → 데이터)와 각 도메인의 `init`/`validate`/`plan` 명령을 모두 노출한다.
- 각 도메인 문서에 입력 계약(필요한 remote-state output, 필수 권한, 적용 전제조건)과 출력 계약을 명시한다.
- 한 도메인의 output 값에 영향을 주는 변경이 있으면, 그 변경과 함께 의존 도메인의 plan 결과도 같이 검토한다.

향후 다른 리전/환경에 같은 네트워크·데이터베이스 구성을 반복 배포해야 하는 시점에는, 공통 모듈(`modules/`)과 환경별 독립 state(`envs/<환경>/<도메인>/`)를 조합하는 확장 구조를 검토 대상으로 남겨뒀다.
이 구조는 코드가 있는 위치와 state가 생기는 위치를 분리해, 구조 1의 state 격리·독립 적용 장점을 유지하면서 구조 3-a의 재사용성 장점도 함께 가져갈 수 있다.
다만 기존 리소스 정의를 공통 모듈 쪽으로 옮기고 각 환경에서 변수화하는 리팩터링이 필요하고, resource address가 바뀌므로 `moved` 블록이나 state 이전 절차가 동반돼야 한다 — 지금 당장 전환할 필요는 없고, 반복 배포 요구가 실제로 생겼을 때 검토하는 확장안으로 남겨뒀다.
