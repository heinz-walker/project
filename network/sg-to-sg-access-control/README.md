<div align="center">
<h1>SG-to-SG 체이닝 기반 최소권한 네트워크 통제 설계</h1>
<i>Least-Privilege Network Control via Security-Group Chaining</i>
</div>

*2025.06 · 정보보안 담당*

---

## 1. 요약
전사 AWS 인프라의 보안그룹(SG) 정책이 CIDR 또는 전체 허용 기반으로 열려 있는 현황을 진단하고, SG를 서로를 참조하는 방식으로 체이닝해 최소권한 통제로 전환하는 설계를 검토했다.
2-tier·3-tier·ALB 진입점 등 실제 구성 패턴별 설계 예시를 만들고, SG 체이닝만으로는 막을 수 없는 외부 API 호출 구간에는 별도 통제 계층(Network Firewall 또는 프록시)을 추가하는 보완책까지 정리했다.
이 검토가 이후 회사 표준 네트워크 아키텍처로 발전했다.

---

## 2. 배경
인바운드는 대부분 CIDR 기반 대역 허용, 아웃바운드는 사실상 전체 허용에 가까운 정책으로 운영되고 있었다.
서버 하나가 침해되면 내부 전체로 옆으로 퍼지기(lateral movement) 쉬운 구조였고, 환경(Stage/Live) 간 경계도 네트워크 정책만으로는 명확히 나뉘어 있지 않았다.
SG 단위로 통신을 제어하지 않으니 어떤 트래픽이 왜 허용되는지 로그로 추적하기도 어려웠다 — 이 문제의식에서 SG 자체를 서로 참조하는 방식으로 바꾸는 설계를 검토하게 됐다.

---

## 3. 담당 역할
- 현황 진단 — 인바운드/아웃바운드 정책 현황 조사, 위험 시나리오 정리
- 설계 — 2-tier·3-tier·ALB 진입점 등 구성 패턴별 SG-to-SG 체이닝 설계 예시 작성
- 한계 분석 및 보완책 제시 — SG 체이닝만으로 통제되지 않는 구간(외부 API 호출) 식별과 대안 설계
- 도입 계획 수립 — 개선 순서, 기대효과 정리 및 제안

---

## 4. 진행 과정
### 4.1. 현황 진단과 위험 시나리오 정리
> 아웃바운드 정책이 사실상 통제 없이 열려 있다는 것을 확인하고, 이것이 실제로 어떤 사고로 이어질 수 있는지 유형별로 정리했다.

인바운드는 전체 개방, 아웃바운드는 Default SG(자기 자신을 소스로 하는 규칙) 기준 전체 허용 — 사실상 통제가 없는 상태였다.
보안 사고 중 정보 유출 사고의 상당수가 열린 아웃바운드 경로를 통해 발생한다는 문제의식으로, 실제로 생길 수 있는 위험을 세 유형으로 정리했다: 내부 서버가 침해됐을 때 외부로 데이터를 빼가는 경로(정보유출), 환경 간 경계가 없어 Stage 환경에서 Live 환경으로 잘못 접근하는 경로(환경 간 무단 접속), 침해된 서버가 외부 C2 서버와 통신하는 경로(2차 공격).
세 유형 모두 공통 원인은 하나였다 — 아웃바운드를 막지 않으면 내부의 어떤 문제든 외부로, 또는 다른 환경으로 확산될 수 있다는 것.

### 4.2. SG-to-SG 체이닝 설계
> 보안그룹이 서로를 참조하도록 구성해, 명시적으로 허용한 SG만 통신할 수 있게 설계했다.

AWS 보안그룹은 상태 저장(Stateful) 방식이라, 한쪽에서 나가는 연결을 허용하면 그에 대한 응답 트래픽은 별도 규칙 없이 자동으로 허용된다는 특성을 활용해, 최소한의 규칙만으로 필요한 통신만 열리도록 설계했다.
2계층 구성(A→B)은 A의 아웃바운드에서 B의 SG를 목적지로, B의 인바운드에서 A의 SG를 출발지로 지정하는 방식으로 규칙을 최소화했다.
Web→App→DB처럼 한 서버가 앞단에서는 서버 역할, 뒷단에서는 클라이언트 역할을 하는 3계층 구성에서는, 같은 인스턴스에 역할별로 서로 다른 SG를 복수 부착해 앞뒤 계층을 명확히 분리했다.
인터넷 진입점(ALB)은 SG 체이닝의 예외로 두되, 전체 개방을 ALB의 인바운드 포트 하나로만 한정하고 그 뒤의 모든 내부 구간은 SG 체이닝으로만 연결되도록 설계했다.

### 4.3. 한계와 보완책
> SG 체이닝만으로는 막을 수 없는 구간(외부 API 호출)을 식별하고, 별도 통제 계층을 추가하는 두 가지 대안을 제시했다.

내부 인스턴스가 외부 API(클라우드 서비스, 패키지 저장소, 보안 업데이트 등)를 호출해야 하는 경우, 목적지가 내부 SG가 아니므로 SG 체이닝만으로는 대응할 수 없었다.
이 구간에는 두 가지 대안을 제시했다 — 외부로 나가는 트래픽을 Network Firewall로 도메인/IP 단위 허용목록으로 관리하는 방식과, 프록시 서버 경유를 강제하고 AWS Prefix List로 허용 대상을 관리하는 방식이다.
두 방식 모두 "내부는 SG-to-SG로 최소권한 통제, 외부 연결이 꼭 필요한 구간만 별도 통제 계층을 추가한다"는 같은 원칙을 따랐다.
또한 AWS 계정 생성 시 자동으로 만들어지는 Default 보안그룹이 같은 SG를 쓰는 인스턴스끼리 사실상 무제한 통신을 허용하는 문제도 함께 짚어, 서버 간 직접 접근 경로를 막고 반드시 점프 서버(Bastion)를 거치도록 하는 원칙을 함께 제안했다.

### 4.4. 개선 순서와 기대효과
> 전체 SG를 한 번에 바꾸는 대신, 아웃바운드부터 단계적으로 전환하는 순서를 제시했다.

먼저 전체 SG의 아웃바운드 규칙을 조사하고, 불필요한 전체 허용 규칙을 SG 기반 대상 지정으로 하나씩 교체한 뒤, 마지막으로 인바운드 정책도 CIDR 기반에서 SG 기반으로 전환하는 순서를 제안했다.
이 순서를 통해 통신 경로가 명확해지고, 정책이 SG에 귀속되므로 오토스케일링이나 재배포 상황에서도 같은 SG만 할당하면 규칙이 자동으로 유지되며, 인증·감사 대응에 필요한 통제 증적도 함께 확보할 수 있다는 점을 기대효과로 제시했다.

---

## 5. 성과 및 배운 점
- 아웃바운드가 열려 있을 때 생기는 위험을 추상적인 "최소권한 원칙 위배"가 아니라 실제 사고 시나리오(정보유출/환경 간 무단접속/2차 공격) 세 가지로 구체화해, 왜 바꿔야 하는지를 설득력 있게 전달할 수 있었다.
- SG 체이닝이라는 하나의 원칙을 2-tier/3-tier/ALB 진입점처럼 실제 구성 패턴별로 구체적인 설계 예시로 풀어낸 것이, 이후 실제 구축 단계에서 그대로 참조할 수 있는 기준이 됐다.
- 새로운 통제 방식을 제안할 때는 이상적인 모델만 제시하는 것이 아니라, 그 모델이 못 막는 구간(외부 API 호출)을 스스로 짚고 보완책까지 함께 제시해야 실행 가능한 제안이 된다는 것을 확인했다.
- 이 검토서에서 제안한 SG-to-SG 체이닝과 외부 통제 계층 결합 원칙은 이후 회사의 표준 네트워크 아키텍처로 발전해 실제로 구축·적용됐다.
