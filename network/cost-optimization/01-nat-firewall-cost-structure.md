<h1>Network Firewall·NAT Gateway 비용 구조 분석</h1>
<i>Cost Structure Analysis of AWS Network Firewall and NAT Gateway</i>
</div>

*2026.09 · 클라우드 인프라 비용 분석*

---

## 1. 요약
방화벽 표준화로 VPC마다 Network Firewall과 NAT Gateway를 두는 구조가 됐고, 두 서비스의 요금이 겹쳐 청구되는지와 어디서 비용이 나가는지를 실측으로 확인했다.
NAT를 방화벽과 같은 경로에 두면 NAT 요금이 방화벽 사용량만큼 상쇄되는 AWS 공식 정책이 있고, VPC 4개의 실제 라우팅으로 모두 이 조건을 만족함을 확인했다.
NAT 요금이 전액 상쇄된다고 가정하면(운영 VPC의 방화벽 처리량이 안정화 후 NAT 수준에 수렴한다는 추정 포함) 비용 대부분이 방화벽이고, 방화벽 비용의 약 87%는 트래픽과 무관한 엔드포인트 고정 시간당 요금이다.
이 구조에서는 트래픽이 거의 없는 VPC에도 운영 VPC와 거의 같은 고정비가 붙는다.
운영 VPC가 전체 NAT 트래픽의 99.7%를 차지하고, 현재 엔드포인트 수와 구성을 유지한다면 엔드포인트를 켜 두는 시간이 가장 큰 절감 요인이다.

---

## 2. 배경
방화벽 표준화([아키텍처 표준화](../architecture-standardization/))로 모든 VPC에 방화벽 엔드포인트를 AZ마다 하나씩 두게 됐다.
엔드포인트는 사용 여부와 관계없이 시간당 요금이 붙는다. 표준을 적용할수록 고정비가 늘어나는 구조다.
여기에 NAT Gateway도 같은 경로에 있어서, 두 요금이 이중으로 청구되는지부터 확인해야 했다.
이중 부과라면 구조를 바꿔야 하고, 아니라면 어디를 줄일 수 있는지가 다음 질문이었다.
정확한 청구 데이터는 결제 계정 권한이 필요해 접근할 수 없었기 때문에, 사용량을 직접 조회해 공식 단가로 계산하는 방식을 택했다.

---

## 3. 담당 역할
- 요금 면제 정책의 조건 확인과 실제 라우팅 기반 검증
- 서울 리전 공식 단가 확보
- CloudWatch 지표로 NAT와 방화벽 트래픽 실측
- 월 비용 추정과 절감 가능 지점 도출

---

## 4. 진행 과정
### 4.1. 면제 정책 확인 — 조건과 상한을 먼저
> NAT를 방화벽과 같은 경로에 두면 NAT 요금이 방화벽 사용량만큼 상쇄된다는 공식 조항을 확인했다.

AWS Network Firewall 요금 페이지의 NAT Gateway 면제 조항을 읽고 세 가지를 확인했다.
조건은 NAT를 나온 트래픽이 반드시 방화벽을 거치는 같은 경로여야 한다는 것이다.
상한은 방화벽의 엔드포인트 시간당 사용량과 GB당 처리량에 1:1로 맞춰지는 만큼만 면제된다는 것이다. NAT 사용량이 더 많으면 초과분은 정상 과금된다.
청구 방식은 NAT 요금(양수)과 별도 차감 항목(음수)으로 상쇄되는 것이라, 리소스가 0원으로 보이지 않는다.
방화벽 자체 비용은 면제 대상이 아니라는 점도 여기서 확인했다.

### 4.2. 라우팅 검증 — 문서의 조건을 우리 환경에 대입
> 정책이 있다는 것과 우리 환경이 그 조건을 만족하는 것은 다른 문제라서, 라우팅 테이블을 직접 조회했다.

VPC 4개(운영, Stage, Dev, 레거시)의 라우팅 테이블을 조회해 같은 경로 여부를 확인했다.
운영, Stage, Dev는 나가는 방향이 private → NAT → 방화벽 엔드포인트 → IGW이고, 들어오는 방향은 IGW → 방화벽 엔드포인트 → NAT여서 양방향 모두 방화벽을 거친다.
레거시 VPC는 방화벽과 NAT의 순서가 반대지만 같은 경로 안에 있어 조건을 충족했다.
VPC마다 방화벽 엔드포인트 수(2)와 NAT 수(2)가 같다는 점도 상한 조건에 맞는다.

### 4.3. 단가와 실측 — 공식 문서의 한계를 우회
> 공식 요금 페이지는 서울 리전 단가가 없어 Price List API로 확보했고, 트래픽은 31일 지표로 실측했다.

공식 요금 페이지에는 다른 리전의 예시만 있었다. Price List API로 서울 리전 단가를 직접 조회했다.

| 항목 | NAT Gateway | Network Firewall(표준 엔드포인트) |
| --- | ---: | ---: |
| 시간당 | $0.059 | $0.395 |
| GB당 처리 | $0.059 | $0.065 |

4개 VPC의 NAT 8개와 방화벽 4개에 대해 31일 CloudWatch 지표를 조회했다.
운영 VPC가 전체 NAT 트래픽의 99.7%를 차지했고, 나머지는 무시할 수준이었다.

실측값에는 왜곡이 있었다.
운영 VPC 방화벽의 31일 합계가 인라인 전환 이전 27일간 0GB였던 값을 포함하고 있었다.
이 합계로 계산하면 방화벽 처리량이 NAT보다 적게 나와 면제 상한을 잘못 판단하게 된다.
일별로 나눠 보니 전환 후 이틀간의 방화벽 처리량이 같은 기간 NAT 처리량과 같은 자릿수였고, 안정화되면 NAT 수준에 수렴할 것으로 판단해 월 비용 계산에는 이 수렴 추정치를 썼다.

### 4.4. 월 비용 추정 — 고정비가 지배한다
> 사용량과 단가로 계산한 결과, 상쇄 후 비용은 사실상 방화벽 엔드포인트 시간당 요금이다.

VPC당 NAT 2개와 방화벽 엔드포인트 2개, 한 달 744시간을 기준으로 계산했다.

```text
NAT(월)      = 2 × 744h × $0.059/h + GB × $0.059/GB
Firewall(월) = 2 × 744h × $0.395/h + GB × $0.065/GB
```

이 계산에서 값의 성격은 다음과 같이 나뉜다. 실측한 것은 라우팅 경로, 엔드포인트 수, 운영 VPC를 제외한 3개 VPC의 처리량 비교다. 가정한 것은 운영 VPC 방화벽 처리량이 전환 후 정상 운영 월에 NAT 수준에 수렴한다는 점이다. 확인하지 못한 것은 실제 청구 반영 여부다.
그래서 NAT 요금 전액 상쇄는 정상 운영 월을 가정한 추정이며, 전환 전 사용량이 섞인 관측 기간의 청구액과는 다른 계산 대상이다.
남는 방화벽 비용의 약 87%가 트래픽과 무관한 엔드포인트 고정 시간당 요금이다.
이 결과는 트래픽이 거의 없는 VPC(Dev, 레거시)에도 운영 VPC와 거의 같은 방화벽 고정비가 붙는다는 뜻이어서, 환경별로 방화벽을 항상 켜 둘 필요가 있는지가 다음 질문이 됐다([02. Dev 방화벽 운영 방식별 비용 시나리오](./02-dev-firewall-cost-scenarios.md)).
결제 계정의 Cost Explorer는 권한이 막혀 있어 실제 청구액과는 대조하지 못했고, 위 값은 모두 사용량 × 공식 단가로 낸 추정치다.

## 5. 성과 및 배운 점
- 요금 면제 정책을 문서만 믿지 않고 VPC 4개의 실제 라우팅으로 검증했다. 조건 불충족이 하나라도 있으면 NAT 요금이 그대로 청구되는 구조라, 검증 없이 넘길 수 없었다.
- 방화벽 비용의 약 87%가 트래픽과 무관한 고정 시간당 요금임을 수치로 확인했다. 현재 엔드포인트 수와 구성을 유지한다면 켜 두는 시간이 가장 큰 절감 요인이고, 트래픽을 줄이는 효과는 현재 사용량 기준으로 상대적으로 작다.
- 인라인 전환 전 0GB가 섞인 31일 합계가 방화벽 처리량을 과소평가하는 것을 일별 분해로 찾아냈다. 합계만 봤다면 면제 상한을 잘못 판단했을 것이다.
- 공식 문서의 리전 한계(다른 리전 예시만 존재)를 Price List API로 우회해 서울 리전 단가를 확보했다.
- 한계: 실제 청구액과 대조하지 못했다. 모든 금액은 실측 사용량 × 공식 단가로 낸 추정치다.
- 후속 과제: 트래픽이 거의 없는 환경의 방화벽 운영 방식 검토([02](./02-dev-firewall-cost-scenarios.md)). 엔드포인트 수(AZ 수)를 줄이는 방법도 고정비 변수지만 가용성과 맞바꾸는 문제라 이 분석 범위에서는 다루지 않았다.
