## 1. 요약
전자결재 상신·결재 완료, 매체제어 승인요청, 임직원 명부 변경 같은 이벤트를 메일함에서 감시해, 들어온 메일을 JSON으로 선언한 규칙과 대조하고 조건에 맞으면 담당자를 멘션한 슬랙 메시지를 보내는 Python 봇이다.
메시지에는 메일 본문에서 뽑아낸 실행 버튼(문서 열기·승인·반려)을 함께 실어, 슬랙에서 컨텍스트 전환 없이 처리할 수 있게 했다.
규칙은 코드가 아니라 데이터(JSON)로 분리했고, 비개발자가 폼으로 규칙을 만들고 슬랙 메시지 모양을 실시간으로 확인하는 브라우저 빌더와, 메일함·슬랙에 붙이지 않고 규칙 로직을 검증하는 오프라인 테스트 하니스를 함께 만들었다.
현재 5개 규칙을 배포 없이 JSON 편집만으로 운영하며, 조건 변경이 코드 리뷰·배포가 아니라 파일 diff로 끝난다.
설계·구현·테스트 전 과정을 1인으로 진행했다.

---

## 2. 배경
전자결재 상신·결재 완료, 매체제어 승인요청, 임직원 명부 변경 알림을 메일로만 받으면 다른 메일에 묻혀 놓치기 쉽고, "이 중에서 나에게 오는 것"만 골라내기 어렵다.
결재 시스템 자체에는 알림을 커스터마이즈할 여지가 없어서, 시스템이 이미 보내는 메일을 입력으로 삼아 규칙 기반으로 슬랙에 라우팅하기로 했다.
문제는 조건이 자주 바뀐다는 점이었다.
담당자가 바뀌거나, "기안자가 나이고 결재자가 특정인일 때만" 같은 조건이 추가되면 그때마다 코드를 고쳐 배포해야 한다.
그래서 규칙을 코드에서 떼어내 JSON으로 선언하고, 비개발자도 편집할 수 있는 빌더를 붙여, 규칙 변경을 운영 작업으로 만들었다.

---

## 3. 담당 역할
- 규칙 엔진 설계 — 조건(키워드·기안자·결재자·2차 조건·배제 조건·멘션 대상)과 표시(라벨·헤더·버튼·레이아웃)를 한 파일에 선언하는 JSON DSL과 평가 로직
- 메일 파싱 — 서식이 제각각인 결재 메일에서 제목·기안자·결재자·링크를 폴백 체인으로 추출하고 이름을 정규화
- 슬랙 메시지 구성 — 규칙의 표시 옵션으로 Block Kit 블록(헤더·본문·버튼)을 조립, 버튼 URL을 메일 본문에서 동적 추출
- 규칙 빌더 UI — 서버 없이 브라우저 단일 파일로 동작하는 3분할 편집기(폼·슬랙 미리보기·EML 인스펙터)
- 오프라인 테스트 하니스 — 규칙별 positive/negative 케이스 자동 생성, 저장한 실제 메일 기반 검증

## 4. 진행 과정
### 4.1. 규칙을 코드가 아닌 JSON DSL로 분리
> 조건과 표시를 한 파일에 선언해, 규칙 변경이 배포가 아니라 파일 편집으로 끝나게 했다.

규칙을 코드로 하드코딩하면 조건이 바뀔 때마다 배포가 필요하고, 나중에 감사에서 "무슨 기준으로 알림을 보내는가"를 물으면 코드를 읽어야 한다.
그래서 규칙 하나를 JSON 파일 하나로 두고, 그 안에 매칭 조건과 슬랙 표시 방식을 모두 담았다.
조건 쪽은 대상 라벨·제목 키워드·검사 필드(기안자/결재자)·비교 대상(나/리더/직접 입력한 이름 목록/임직원 누구나)·2차 조건·배제 조건으로 구성했고, 표시 쪽은 헤더 문구·노출할 항목·추가 문구·버튼·레이아웃으로 구성했다.

| 규칙 | 조건의 핵심 | 표시 |
| --- | --- | --- |
| 결재 도착 알림 | 기안자가 임직원 누구나 | 제목·기안자 + 문서 열기 버튼 |
| 비용 품의 리더결재 | 기안자 == 나 AND 결재자 in 이름 목록 | 제목·기안자·결재자 + 문서 확인 버튼, 리더 멘션 |
| 내부 품의 리더결재 | 기안자 == 나, 단 결재자 == 나 이면 제외 | 제목·기안자 + 문서 확인 버튼, 리더 멘션 |
| 매체제어 승인요청 | 항상 통과 | 승인·반려·관리콘솔 3버튼 |
| 임직원 명부 변경 | 항상 통과 | 헤더·본문 숨김, 시트 링크만 |

이렇게 나누니 담당자 변경이나 조건 추가가 파일 diff 한 건으로 끝나고, 규칙 목록을 그대로 읽어 "어떤 이벤트가 누구에게 왜 가는지"를 설명할 수 있다.

### 4.2. 메일 파싱의 현실적 문제와 폴백 체인
> 결재 메일마다 사람 이름 표기가 달라서, 추출을 단일 규칙이 아니라 순차 폴백으로 처리했다.

가장 큰 리스크는 메일 서식의 편차였다.
같은 "기안자"라도 어떤 메일은 `기안자: 홍길동`, 어떤 메일은 표의 셀에 `요청자` 행으로, 어떤 메일은 `홍길동님이 … 요청` 문장으로 들어온다.
하나의 정규식으로는 잡히지 않아서, 정규식 → 테이블 셀 파싱 → 문장 패턴 순으로 시도하다 먼저 걸리는 값을 쓰도록 했다.
추출한 이름은 괄호·호칭·공백을 제거해 정규화한 뒤 비교하고, 직접 입력한 이름은 추출값뿐 아니라 본문 전체 텍스트에서도 탐지한다.
`text/html`이 없는 메일은 `text/plain` 본문으로 같은 판단을 하도록 했고, 규칙 평가 중에 메일이 읽음 처리되지 않도록 `BODY.PEEK[]`로 가져온 뒤 실제로 매칭돼 전송할 때만 `\Seen` 플래그를 붙인다.

### 4.3. 슬랙 메시지를 규칙에서 조립
> 헤더·본문·버튼을 규칙의 표시 옵션으로 구성하고, 버튼 URL은 메일 본문에서 링크 텍스트로 동적 추출했다.

메시지 모양을 코드에 고정하면 규칙마다 다른 표현을 쓸 수 없어서, Block Kit 블록을 규칙의 표시 옵션으로 조립하도록 했다.
헤더 문구, 노출할 항목(제목·기안자·결재자·멘션), 인용문 스타일, 추가 문구를 규칙에서 정한다.
버튼은 두 종류다.
고정 URL을 갖는 정적 버튼과, 메일 본문에서 링크 텍스트 키워드로 URL을 찾아내는 동적 버튼("바로가기", "승인 하기", "반려 하기" 등)이다.
매체제어 승인요청은 이 방식으로 승인·반려 버튼을 메시지에 실어, 담당자가 관리콘솔에 들어가지 않고 슬랙에서 바로 처리하게 했다.

### 4.4. 비개발자용 규칙 빌더
> 폼으로 규칙을 만들고 슬랙 메시지 모양을 실시간 미리보기하며, 실제 결재 메일(.eml)을 넣으면 폼을 자동으로 채운다.

규칙을 데이터로 분리해도 JSON을 손으로 쓰게 하면 결국 개발자만 편집할 수 있다.
그래서 브라우저 단일 파일로 동작하는 3분할 편집기를 만들었다.
왼쪽은 폼 편집기, 가운데는 완성될 슬랙 메시지 미리보기, 오른쪽은 EML 인스펙터다.
기존 규칙 JSON을 불러와 수정하거나, 실제 결재 메일 `.eml`을 넣으면 클라이언트 측 MIME 파서가 base64·quoted-printable 디코딩과 문자셋 처리를 거쳐 제목·발신자·수신자·본문·링크·후보 문구를 뽑아 폼을 미리 채운다.
완성한 규칙은 `.json`으로 내려받는다.
백엔드가 없어서 배포할 것도, 접근 권한을 관리할 것도 없다.

### 4.5. 외부 서비스 없이 규칙 검증
> 실제 메일함·슬랙에 붙이지 않고 규칙 로직만 확인하는 오프라인 하니스를 만들었다.

규칙을 바꿀 때마다 실제 메일을 보내 확인할 수는 없어서, 규칙 로직만 떼어 검증하는 하니스를 pytest 없이 작성했다.
합성 모드는 규칙마다 positive 케이스와 negative 케이스(키워드 불일치, 1차 조건 불일치, 2차 조건 불일치, 배제 대상, 본문에서 이름 발견)를 자동 생성해, 평가 함수가 기대한 매칭 결과를 내는지 확인한다.
`--eml` 모드는 저장한 실제 메일 하나를 전체 규칙에 돌려, 어떤 규칙이 걸리는지 본다.
규칙 편집 → 하니스 실행 → 슬랙 미리보기의 순서로, 실 환경에 반영하기 전에 로직을 확정할 수 있다.

### 4.6. 자격증명 분리
> 성격이 다른 값을 세 파일로 나누고 전부 gitignore, 저장소에는 템플릿만 뒀다.

토큰·앱 비밀번호는 `credentials.json`, 채널 ID·메일 계정은 `config.json`, 담당자–슬랙 ID 매핑은 `users.json`으로 나눴다.
민감도와 변경 주기가 다른 값을 한 파일에 두면 실수로 커밋할 위험이 커진다.
세 파일 모두 gitignore하고 저장소에는 `.sample`만 두어, 클론한 사람이 무엇을 채워야 하는지는 알 수 있되 실제 값은 노출되지 않게 했다.

## 5. 성과 및 배운 점
- 5개 규칙을 배포 없이 JSON 편집만으로 운영한다. 결재 도착·완료, 매체제어 승인요청, 임직원 명부 변경을 담당자 멘션과 함께 슬랙으로 자동 라우팅하고, 담당자 변경이나 조건 추가가 코드 리뷰·배포가 아니라 파일 diff로 끝난다.
- 승인·반려·문서 열기 버튼을 메시지에 실어, 담당자가 관리콘솔이나 결재 시스템에 따로 들어가지 않고 슬랙에서 바로 처리하게 했다.
- 메일 서식 편차가 규칙 기반 자동화의 최대 리스크였고, 정규식 → 테이블 파싱 → 문장 패턴의 폴백 체인과 이름 정규화, 그리고 오프라인 테스트 하니스로 흡수했다.
- 규칙을 데이터로 분리하고 비개발자용 빌더를 붙인 덕에, 규칙 변경이 개발 작업이 아니라 운영 작업이 됐다. 자동화의 지속 가능성은 "얼마나 많은 규칙을 넣었는가"보다 "규칙을 누가 어떤 절차로 바꿀 수 있는가"에 달려 있다는 것을 확인했다.
- 시스템이 이미 보내는 메일을 입력으로 삼으면, 결재 시스템에 손대지 않고도 알림 계층을 새로 만들 수 있다. 다만 메일이라는 입력은 서식이 언제든 바뀔 수 있어, 파싱 폴백과 테스트를 함께 갖춰야 안정적으로 유지된다.
