## 1. 요약
위험평가 산식 R = A(자산가치) × T(위협) × V(취약성)에서 A의 근거가 되는 클라우드 자산대장의 품질을 먼저 정비하고, 이어서 취약성(V) 평가를 수작업 대신 자동으로 수행하는 도구를 직접 만들어, 마지막으로 그 결과를 정식 위험평가 결과보고서 체계와 대조해 정합성을 점검한 프로젝트다.
자산대장은 일회성 점검이 아니라 분석 → 개선권고 → 반영 재검토 → 표준 작성 가이드로 정립하는 사이클로 다뤘고, 5개 산출물에 걸쳐 3회 이상 반영-재검토를 반복했다.
위험평가 자동화 도구는 boto3 기반 읽기 전용으로 AWS 주요 서비스 11종에 걸친 14개 항목을 점검하고, 이를 6개 영역으로 분류해 Y(양호)·N(취약)·N/A(해당없음) 3단계로 판정한 뒤 결과를 다중 시트 엑셀(진단 개요·자산 목록·상세 결과)로 생성한다.
발견 건수의 해석 한계 5가지를 리포트에 명시적으로 넣어, 자동 산정 결과가 과대·과소 해석되지 않도록 설계했다.
자동 산정 결과를 정식 위험평가 결과보고서와 대조하는 과정에서 집계 불일치와 수식 참조 오류를 찾아 바로잡았다.

---

## 2. 배경
위험평가를 R = A × T × V로 산정하는데, 정작 A(자산가치)의 근거가 되는 클라우드 자산대장의 신뢰성이 낮았다.
인스턴스의 OS·버전·용도가 비어 있어 취약점 진단 대상조차 특정할 수 없었고, 관리번호가 중복·결번이었으며, 대장에 있으나 실제로는 없는 리소스와 실제로 있으나 대장에 없는 리소스가 섞여 있었다.
이 상태에서 산정한 A는 자산을 잘못 지목하거나 누락하므로, R 전체가 흔들린다.
취약성(V) 평가도 문제였다.
클라우드 보안 설정 점검을 콘솔에서 수작업으로 하면 점검 시점마다 결과가 달라지고, 무엇을 어떤 기준으로 봤는지 재현할 수 없으며, 항목이 늘어날수록 사람이 놓치는 부분이 생긴다.
그래서 (1) 자산대장을 표준 가이드까지 포함해 정비하고, (2) V 평가를 읽기 전용 자동화 도구로 대체하며, (3) 그 산정 결과가 정식 위험평가 보고서 체계와 어긋나지 않는지 점검하는 세 단계로 진행했다.

## 3. 담당 역할
- 클라우드 자산대장 반복 검토 — 데이터 품질·관리번호·자산 범위·컬럼 구조 문제를 유형별로 정리하고, AWS CLI 읽기 전용 조회로 실제 리소스와 대조해 개선권고와 표준 작성 가이드를 작성
- 위험평가 자동화 도구 설계·구현 — boto3 기반 읽기 전용 점검 스크립트, 점검 항목 분류·판정 로직·심각도 산정·다중 포맷 리포트 생성
- 리포트의 진단 개요(범위·방법론·한계) 설계 — 자동 산정 결과의 해석 한계를 문서로 명시
- 자동 산정 결과와 정식 위험평가 결과보고서·상세보고서의 정합성 점검 및 오류 수정

## 4. 진행 과정
### 4.1. 클라우드 자산대장 검토 사이클
> 자산대장을 한 번 점검하고 끝내지 않고, 분석 → 개선권고 → 반영 재검토 → 표준 가이드화의 사이클로 정비했다.

처음에는 자산대장을 문서상으로만 검토했는데, 그렇게 하면 "값이 비어 있다", "번호가 겹친다"까지만 알 수 있고 올바른 값이 무엇인지, 대장 항목이 실물과 맞는지는 확인할 수 없었다.
그래서 검토 방식을 바꿔, `describe-*`·`list-*`·`get-*` 읽기 전용 명령으로 실제 AWS 계정을 조회해 대장과 대조하는 단계를 넣었다.

검토에서 반복적으로 나온 문제는 유형으로 묶으면 다음과 같다.

| 유형 | 내용 |
| --- | --- |
| 필드 값 누락 | 인스턴스 OS·버전·용도, 로드밸런서 용도, 스토리지 버킷 용도, DB 식별자 등 취약점 진단·EOL 관리의 근거가 되는 값이 비어 있음 |
| 관리번호 중복·결번 | 구 사명 기준 항목과 현행 항목이 같은 번호로 공존, 서로 다른 자산에 동일 번호 부여, 중간 번호 누락 |
| 자산 범위 누락 | 일부 계정의 보안 서비스가 대장에 없음, 네트워크·DNS·감사 로그 등 자산 유형 자체가 누락 |
| 비클라우드 자산 혼재 | 온프레미스 물리 서버·네트워크 장비·NAS, 단말 자산, 제3자 SaaS 보안 도구가 클라우드 대장에 섞여 있음 |
| 컬럼 구조 부적합 | 온프레미스 장비용 컬럼(제조사·모델명·고정 IP)이 클라우드 시트에 남아 전부 빈 값이고, 클라우드에 맞는 식별자 컬럼(리소스 ID, DNS 이름, 암호화 여부, 퍼블릭 액세스 여부)이 없음 |
| 실물과 대장 불일치 | 대장에는 있으나 실제로는 없는 리소스, 이름이 바뀌거나 재생성되며 교체된 리소스, 대장에 없는 신규 리소스 |
| 운영 위험 | 지원 종료(EOL)된 OS가 운영 환경에 남아 있는 사례, 이미지와 인스턴스 간 매핑 정보 부재 |
| 관리 공백 | 담당자 없이 '운영 중'으로 등록된 서비스 |

이 문제들을 다섯 개 산출물로 이어지는 사이클로 처리했다.
최초 분석에서는 비클라우드 자산을 식별해 별도 대장으로 분리하도록 권고했고, 이어 1차 수정본을 대상으로 삭제할 컬럼·항목과 추가할 컬럼을 구체적으로 지적했다.
다음 개정본에서 그 권고가 실제로 반영됐는지 재검토했고(반영된 것과 남은 것을 구분), 이 과정을 거쳐 정립된 기준을 앞으로 자산대장을 작성할 때 따를 표준 가이드로 만들었다.
가이드에는 각 시트별로 어떤 값을 어떤 명령으로 확인해 채우는지, 자동 확장 그룹처럼 개별 식별자가 무의미한 경우 무엇을 대신 기재하는지까지 넣었다.
마지막으로 가이드 적용 이후의 개정판을 다시 점검해 잘 반영된 부분과 남은 수정 사항을 확인했다.
한 번의 지적으로 끝내지 않고 반영 여부를 매 라운드 확인하고, 결과를 표준 문서로 고정한 것이 이 단계의 핵심이다.

### 4.2. 위험평가 자동화 도구 설계·구현
> 취약성 평가를 boto3 읽기 전용 자동화로 대체하고, 자동 산정 결과의 해석 한계를 리포트에 명시적으로 넣었다.

스크립트 전체는 [`code/`](./code/)에 있다(`run_assessment.py`, 설정 템플릿 `settings.json.example`).

**읽기 전용 원칙.**
스크립트는 조회 계열 API만 호출하고 리소스를 생성·수정·삭제하지 않는다.
이렇게 하면 운영 환경에서 별도 승인 없이 반복 실행할 수 있고, 점검 자체가 사고를 유발할 여지가 없다.
정기적으로 같은 조건으로 돌려 시점 간 비교가 가능하다는 점도 수작업 대비 이점이다.

**점검 항목과 분류.**
점검 항목은 EC2 인스턴스 현황, Inspector 취약점(Critical/High), Security Group의 위험 포트·0.0.0.0/0 노출, IAM AdministratorAccess 보유 주체, MFA 미적용 사용자, 오래된 액세스 키(90일 초과), S3 퍼블릭 액세스, EBS 볼륨 암호화, CloudTrail·GuardDuty·Security Hub·AWS Config 활성화, RDS 퍼블릭 액세스, EBS 스냅샷 공개 공유로 구성했다.
이를 인프라 현황·취약점 관리·네트워크 보안·접근 제어·데이터 보호·보안 모니터링 6개 영역으로 분류했다.
위험 포트는 SSH·RDP·주요 DB 포트 등 26개를 목록으로 관리하고, 키 교체 기준일 같은 값은 설정 파일로 분리해 코드 수정 없이 조정할 수 있게 했다.

**판정 로직.**
판정은 Y(양호)·N(취약)·N/A(해당없음) 3단계이고, 항목 성격에 따라 집계 방식을 다르게 뒀다.
CloudTrail·GuardDuty처럼 계정 단위로 켜고 끄는 설정형 항목은 활성화 여부 1건으로 판정한다.
위반 사례를 나열하는 항목(노출된 Security Group 규칙, 암호화 안 된 볼륨 등)은 발견 건수를 그대로 취약 건수로 집계한다.
EC2 인스턴스 목록은 취약 판정 대상이 아니라 현황 파악용이므로 N/A로 분리했다.
각 항목의 판정 기준 문장을 코드에 함께 저장하고 결과 시트에 "진단 기준" 열로 출력해, 판정 근거를 표에서 바로 확인할 수 있게 했다.
심각도는 Inspector가 주는 등급을 그대로 쓰거나, Security Group은 열린 포트가 DB 포트인지 관리 포트인지에 따라 규칙으로 산정한다.

**리포트 생성.**
결과는 원본 JSON, 요약 CSV, 열람용 HTML, 보고용 엑셀 네 가지로 출력한다.
엑셀은 정식 위험평가 상세보고서 체계에 그대로 넣을 수 있도록 세 시트로 구성했다.
진단 개요 시트에는 진단 대상·범위·방법론과 함께 한계를 적었고, 자산 목록 시트에는 영역별 집계를, 상세 결과 시트에는 개별 발견 항목을 심각도·리소스·현황·조치 방법과 함께 넣었다.

**한계를 리포트에 명시한 설계 선택.**
자동화 스캔 결과는 그대로 두면 과대 또는 과소 해석되기 쉬워서, 다음 다섯 가지 한계를 진단 개요 시트에 고정 문구로 넣었다.

| 한계 | 내용 |
| --- | --- |
| 집계 기준 | "전체/취약" 건수는 발견된 위반 사례 수이며, 전체 자산 모집단 대비 비율이 아니다. 양호한 리소스 수는 별도로 집계하지 않는다. |
| 취약점 등급 범위 | Inspector 취약점은 Critical/High만 조회하며 Medium/Low는 포함하지 않는다. |
| 진단 레벨 | 인프라·클라우드 설정 레벨에 한정하며, 애플리케이션 코드·웹 취약점은 범위 밖이다. |
| 시점 | 진단 일시 기준 스냅샷이며 이후 설정 변경은 반영되지 않는다. |
| 설정형 항목 | CloudTrail·GuardDuty·Security Hub·AWS Config는 계정 단위 활성화 여부만 확인하고, 세부 규칙·정책 수준은 검증하지 않는다. |

이렇게 한 이유는, 자동 산정 결과가 정식 위험평가 보고서에 인용될 때 "몇 건 발견"이라는 숫자만 옮겨지면 마치 전체 자산 대비 비율처럼 읽히기 때문이다.
EBS 스냅샷 공개 여부를 소유 계정 스냅샷만 대상으로 본다거나, 설정형 항목을 계정 단위로만 본다는 점도 같은 맥락에서 명시했다.
점검 범위를 넓히는 것보다, 지금 보는 범위가 어디까지인지 리포트가 스스로 밝히도록 하는 쪽을 택했다.

### 4.3. 결과 체계 점검
자동 산정 결과를 정식 위험평가 결과보고서·상세보고서와 대조하며 정합성을 점검했다.
같은 파일 안에서 요약 시트와 상세 시트의 집계 숫자가 서로 다른 문제, 판정값이 들어 있는 열이 아니라 옆의 서술 텍스트 열을 참조해 이행률이 항상 0%로 계산되던 수식 오류를 찾아 바로잡았다.
R = A × T × V 산식이 문서에 선언만 되어 있고 실제 산정에는 쓰이지 않던 점도 확인해, 자산대장 기반으로 A를 실제로 반영하도록 정리했다.
이 과정에서 자동화 스캔이 계정 전체를 훑다 보니 인증 범위 밖 자산까지 함께 진단된다는 점이 드러나, 자산대장과 대조해 범위를 보정했다.
자세한 재분류 내용은 별도 보고서에서 다뤘고, 여기서는 자동 산정과 정식 보고서 체계를 연결할 때 집계 기준을 맞춰야 한다는 점만 기록한다.

## 5. 성과 및 배운 점
- 클라우드 자산대장을 5개 산출물에 걸쳐 3회 이상 반영-재검토하며 정비하고, 그 결과를 표준 작성 가이드로 고정했다. 데이터 품질·관리번호·자산 범위·컬럼 구조·실물 불일치를 유형별로 정리해, 이후 대장 작성 시 같은 기준을 재사용할 수 있게 했다.
- 취약성 평가를 boto3 읽기 전용 자동화 도구로 대체했다. AWS 11종 서비스 14개 항목을 6개 영역으로 나눠 3단계로 판정하고, 4가지 포맷 리포트를 생성한다. 콘솔 수작업 대비 점검 결과의 재현성과 시점 간 비교 가능성을 확보했다.
- 자동 산정 결과의 해석 한계 5가지를 리포트 자체에 명시해, 정식 위험평가 보고서에 인용될 때 발생하던 과대·과소 해석 여지를 줄였다.
- 자동 산정 결과와 정식 보고서를 대조해 집계 불일치와 수식 참조 오류를 바로잡았다.
- 자산가치의 근거 데이터가 부실하면 위험평가 전체가 흔들린다는 것을 확인했다. R = A × T × V에서 A를 뒷받침하는 자산대장부터 정비하지 않으면, 정교한 산식도 잘못된 대상을 평가하게 된다.
