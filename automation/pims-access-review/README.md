<h1>개인정보처리시스템(PIMS) 접속 이력 감사 자동화</h1>
<i>PIMS Access Log Audit Automation</i>
</div>

*2026.03 · 정보보안 담당*

---

## 1. 요약
개인정보처리시스템(PIMS) bastion host 접속 로그와 별도로 운영되는 게임 서비스 관리툴 접속 로그를 매월 자동으로 수집·대조해, 검토자가 바로 판단에 쓸 수 있는 HTML 요약 보고서와 XLSX 상세 내역으로 만들어주는 도구다.
CloudTrail·CloudWatch Logs에서 SSM 세션 이벤트와 실행 명령을 복원하고, 명령을 위험 카테고리 6종으로 태깅한 뒤 그 위에 규칙 엔진을 올려 반복되는 정상 패턴을 자동으로 "이상없음"으로 분류한다.
감사 항목은 비인가자 접속, 업무시간 외 접속, 과도한 명령어 수행, 불필요 접속시도 차단 4종이며, 여기에 게임 서비스 3종의 관리툴 로그인·민감 처리행위 이력을 상관분석해 같은 보고서에 싣는다.
2026년 3월부터 5개월 연속 실사용하며 정제 로직과 자동 판정 규칙을 반복 보완했다.
설계·구현·운영 전 과정을 1인으로 담당했다.

---

## 2. 배경
개인정보보호법·ISMS-P 성격의 상시 감사 의무에 따라, 개인정보처리시스템 접속 이력을 매월 점검해야 했다.
문제는 점검 자체가 매번 수작업이었다는 점이다.
CloudTrail 원본 로그와 CloudWatch Logs에 남은 세션 스트림을 매번 대조해 실제 실행된 명령을 확인하는 데 시간이 오래 걸렸고, 세션 출력은 ANSI 이스케이프와 쉘 프롬프트가 뒤섞여 있어 그대로는 읽기도 어려웠다.
더 큰 비효율은 따로 있었다.
업무시간 내 인가된 사용자의 접속, 표준 운영 계정으로 전환하는 명령처럼 매달 똑같이 반복되는 정상 패턴까지, 매번 처음 보는 것처럼 사람이 판단해야 했다.
그래서 자동화의 목표를 "전부 자동으로 판정한다"가 아니라 "반복되는 정상 패턴은 규칙으로 걸러내고, 사람은 규칙에 걸리지 않은 예외만 보게 한다"로 잡았다.

---

## 3. 담당 역할
- 감사 항목·판정 기준 설계 — bastion 접속 감사 4개 항목과 웹 관리툴 로그 상관분석 범위 정의
- CloudTrail S3·CloudWatch Logs 수집 자동화 구현 — 세션 이벤트 추출, 세션 스트림 명령 복원 및 정제
- 위험 분류·규칙 기반 자동 판정 엔진 설계·구현 — 정규식 위험 패턴, 조건 매칭 규칙 엔진, 승인 오버라이드
- 웹 관리툴 로그 상관분석 로직 구현 — 게임 서비스별 시트 파싱, 민감 처리행위 탐지
- HTML/XLSX 보고서 생성 및 5개월 반복 운영 — 매월 실행하며 규칙·정제 로직 보완

## 4. 진행 과정
### 4.1. CloudTrail 로그 수집과 SSM 세션 재구성
> 매일 CloudTrail 로그를 S3에서 동기화하고, 세션 스트림에서 실행 명령을 복원해 사람이 읽을 수 있는 텍스트로 만들었다.

검토 대상 기간의 날짜별로 S3에서 그날 CloudTrail 로그를 동기화한 뒤, SSM StartSession/ResumeSession/TerminateSession 이벤트만 추출했다.
접속 성공 이벤트와 차단(오류코드 포함) 이벤트를 이 단계에서 나눠, 이후 서로 다른 검토 흐름을 타도록 했다.
접속 성공 이벤트의 세션 ID로 CloudWatch Logs의 세션 스트림을 조회해 실제 실행된 명령어를 가져왔는데, 원본은 ANSI 컬러 이스케이프·커서 제어 문자·쉘 프롬프트 문자열이 뒤섞여 있어 그대로는 사람이 읽을 수도, 정규식으로 명령을 판별할 수도 없었다.
이스케이프·제어문자 제거, 반복되는 프롬프트 접두어 제거, welcome 배너 같은 잡음 줄 제외, 알려진 명령 접두어 화이트리스트 매칭 순으로 정제 로직을 여러 번 다듬어 지금 형태로 정리했다.
세션 시작 시 프롬프트만 나오고 실제 명령이 없는 줄은 걸러내, 이후 위험 분류 단계에는 실제 명령 문자열만 넘어가게 했다.

### 4.2. 명령어 위험 분류와 규칙 기반 자동 판정
> 정규식으로 명령을 위험 카테고리로 먼저 태깅하고, 그 위에 규칙 엔진을 올려 반복되는 정상 패턴은 자동으로 "이상없음"으로 분류되게 했다.

정제된 명령어를 정규식 기반 위험 패턴 6종으로 먼저 태깅했다.

| 위험 카테고리 | 판별 기준 |
| --- | --- |
| 자격증명 노출 | 비밀번호·시크릿·토큰·개인키 관련 키워드가 포함된 명령 |
| DB 직접 접근 | mysql·psql·redis-cli·mongosh 등 DB 클라이언트 실행 |
| 권한 변경 | sudo·su·chmod·chown·usermod·visudo 등 권한 관련 명령 |
| 서비스 제어 | systemctl·docker·kubectl 등 서비스·컨테이너 제어 명령 |
| 데이터 아카이브 | tar·scp·rsync·mysqldump 등 데이터 이동·백업 명령 |
| 파괴적 명령 | rm -rf·drop table·delete from 등 파괴적 명령 |

이 태그만으로는 "위험해 보이는 명령을 실행했다"만 알 수 있고, 그 실행이 정당했는지는 알 수 없었다.
그래서 태그 위에 규칙 엔진을 하나 더 올려, "누가/언제/어떤 명령을 실행했는가"를 대조했다.
규칙은 배열 순서대로 조건을 매칭해 처음 일치하는 규칙을 적용하는 구조로 짰다.
예를 들어 운영 표준 계정으로 전환하는 `sudo su - <서비스계정>` 패턴처럼 매달 반복되는 정상 명령은 규칙 하나로 "이상없음(양호)"으로 자동 분류되고, 나머지는 조건 없는 catch-all 규칙이나 "확인 필요"로 남는다.
대안으로 위험 태그가 붙은 명령을 예외 없이 매번 사람이 검토하는 방식도 검토했지만, 매달 같은 표준 계정 전환·같은 DB 접속 패턴이 반복되는 걸 알면서도 매번 처음부터 판단하게 하는 건 낭비라고 판단해 규칙 엔진 쪽을 택했다.
규칙으로 못 걸러낸 개별 세션·이벤트는 사람이 판단을 내린 뒤 세션 ID·이벤트 ID를 키로 하는 승인 오버라이드에 기록해두면, 자동 규칙보다 우선 적용되어 같은 세션을 다시 판단할 필요가 없어진다.

### 4.3. 업무시간 외·공휴일 판별과 IP 허용목록
> 야간·휴일 접속은 그 자체로 예외 검토 대상이라는 감사 요구에 맞춰, 업무시간·공휴일·허용 IP를 코드가 아닌 설정값으로 분리했다.

개인정보처리시스템 접속은 업무시간 내 인가된 목적의 접속이 원칙이고, 야간·주말·공휴일 접속은 장애 대응 같은 예외적 사유가 없는 한 그 자체로 감사 대상이 된다는 요구가 있었다.
업무시간 시작·종료 시각을 인수로 받아, 평일 해당 범위를 벗어나거나 주말·공휴일에 해당하면 "업무시간 외"로 표시하도록 구현했다.
공휴일은 매년 초 갱신해야 하는 값이라 코드에 넣지 않고 설정 파일의 날짜 배열로 뺐다.
허용 IP는 단일 IP 목록과 CIDR 대역(사내망 등) 두 가지로 관리해, 접속 IP가 어느 쪽에도 속하지 않으면 표시 레이블 없이 원본 IP를 그대로 노출시켜 검토자가 바로 알아채게 했다.

### 4.4. 웹 관리툴 로그 상관분석
> bastion 접속뿐 아니라 그 접속으로 실제 무엇을 했는지까지가 감사 대상이라는 점에서, 게임 서비스 관리툴 접속 로그를 같은 보고서에 합쳤다.

별도로 담당자에게 받는 게임 서비스 관리툴(웹앱) 접속 로그 엑셀을 게임 서비스별 시트로 파싱해, 로그인 이력뿐 아니라 정지 처리·재화 변경·VIP 변경·아이템 변경·메시지 발송 같은 민감 처리행위 여부까지 같은 보고서에 실었다.
bastion 접속 로그만 감사하면 "누가 언제 접속했는가"는 확인되지만, 그 접속으로 실제 무엇을 했는지는 별도 로그를 봐야 알 수 있다.
두 로그를 따로 검토하면 검토자가 매번 두 문서를 오가며 대조해야 하므로, 한 보고서 안에서 bastion 접속 여부와 웹앱 상의 실제 처리행위를 나란히 볼 수 있게 했다.
웹앱 로그 원본에는 실패 로그인이나 접근 차단 이벤트가 없어, 이 한계는 보고서의 검토 한계 표에 그대로 명시해 검토자가 이 보고서가 보는 범위가 어디까지인지 알 수 있게 했다.

### 4.5. 보고서 산출과 반복 운영
> 전자결재 첨부용 HTML과 근거 확인용 XLSX 두 가지로 내보내고, 5개월 실사용하며 정제 로직과 규칙을 자연스럽게 다듬었다.

결재 시스템에 올릴 요약본(HTML)과 검토자가 개별 건의 근거를 확인할 상세 내역(XLSX, 시트별 원시 이벤트와 검토 결과)을 함께 생성했다.
결재 문서에는 요약과 결론만 필요하고, 실제 근거 확인은 상세 표에서 이뤄지는 등 두 문서의 역할이 다르기 때문이다.
첫 달 실행에서는 정제 로직이 걸러내지 못한 프롬프트 잔여 문자열, 화이트리스트에 없는 정상 명령 접두어, catch-all 규칙 부재로 매번 "확인 필요"로 뜨는 반복 패턴이 있었고, 이후 2026년 3월부터 7월까지 다섯 달 동안 실사용하며 규칙과 정제 로직을 점진적으로 보완했다.
AWS 세션이 만료된 상태에서 CSV는 이미 있고 HTML만 다시 만들어야 하는 경우를 대비해, AWS 접근 없이 저장된 CSV를 읽어 HTML/XLSX만 재생성하는 경로도 별도로 마련해뒀다.

## 5. 성과 및 배운 점
- bastion 접속 로그와 웹앱(게임 서비스 3종) 관리툴 로그를 감사 항목 4종(비인가자 접속, 업무시간 외 접속, 과도한 명령어 수행, 차단 이력) 기준으로 자동 판정해, 검토자가 규칙에 걸리지 않은 예외 건만 보면 되는 구조로 만들었다.
- 2026년 3월부터 5개월 연속 실사용하며 정제 로직과 자동 판정 규칙을 반복 보완해, 매달 반복되는 정형 패턴(표준 계정 전환, 업무시간 내 인가자 접속 등)에 대한 수작업 재판단을 없앴다.
- 규칙 기반 자동화의 핵심은 "정확한 자동 판정"이 아니라 "사람이 뭘 봐야 하는지 좁혀주는 것"이라는 점을 확인했다. catch-all 규칙이 항상 남아 있어 규칙이 놓친 건은 결국 사람이 다시 보게 되고, 자동화는 반복되는 뻔한 판단만 대신한다.
- 반자동 설계(자동 규칙 + 사람의 승인 오버라이드가 최종 결정권을 가지는 구조)를 택한 이유는, 개인정보처리시스템 접속 감사처럼 놓친 이상 접속의 비용이 불필요한 재검토의 비용보다 훨씬 큰 업무에서는 완전 자동 판정보다 사람이 언제든 뒤집을 수 있는 구조가 더 안전하기 때문이다.
