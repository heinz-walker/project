<h1>바이브 코딩 보안 가드레일 표준(안) 수립</h1>
<i>Security Guardrails for AI-Assisted ("Vibe") Coding</i>
</div>

*2026.02 · 정보보안 담당*

---

## 1. 요약
AI 코드 생성 도구를 업무에 쓰는 과정에서 생길 수 있는 정보 유출·취약점 혼입·권한 남용 위험을 통제하기 위한 보안 가드레일 표준안을 만들었다.
프레임워크를 먼저 세우지 않고, 실제로 어떤 도구가 어떻게 쓰이고 있고 어떤 경로로 위험이 생기는지부터 점검 항목으로 정리한 뒤 표준안 초안을 작성했다.
표준안은 허용 도구 정책, 프롬프트에 포함하면 안 되는 정보의 범위, 시크릿 스캐닝·컨텍스트 제외 규칙 같은 기술적 가드레일, 생성 코드 검증 절차로 구성했다.

---

## 2. 배경
AI 코드 생성 도구는 이미 여러 팀에서 실제로 쓰이고 있었지만, 이 도구들을 어떻게 안전하게 써야 하는지에 대한 사내 기준은 없었다.
일반적인 코드 보안 기준(시크릿 관리, 코드 리뷰)은 있었지만, AI 도구 특유의 위험 — 프롬프트에 민감정보가 그대로 들어가는 경로, 에이전트가 파일을 직접 수정·실행하는 권한, 외부 연동(MCP 등)을 통해 들어오는 입력 — 은 다루고 있지 않았다.
그래서 일반론적인 "AI 사용 정책"을 위에서 정하는 대신, 실제 위험 경로를 먼저 나열하고 그 경로를 막는 기술적 가드레일과 표준을 함께 제안하는 방식으로 접근했다.

---

## 3. 담당 역할
- 위험 요소 식별 — AI 코딩 도구 특유의 위험 경로(민감정보 노출, 시크릿 하드코딩, 프롬프트 인젝션, 과도한 에이전트 권한 등) 정리
- 기술적 가드레일 설계 — 시크릿 스캐닝, 컨텍스트 제외 규칙, 에이전트 권한 최소화, 실행 환경 격리 방안 제안
- 보안 프롬프트 표준안 작성 — 민감정보 마스킹, 금지 행위, 검증 절차를 담은 표준 초안 작성
- 외부 프레임워크 검토 — OWASP Top 10 for LLM Applications, NIST AI RMF 등과 대조해 누락 항목 점검

---

## 4. 진행 과정
### 4.1. 위험 경로부터 정리
> 표준을 먼저 만들지 않고, AI 코딩 도구를 쓸 때 실제로 무엇이 새는지부터 나열했다.

일반 코드 보안 기준을 그대로 가져다 붙이면 "AI가 생성한 코드도 리뷰한다" 정도의 뻔한 항목만 남는다.
AI 코딩 도구가 기존 개발 방식과 다른 지점은 프롬프트·컨텍스트로 무엇이 넘어가는지, 에이전트가 파일·명령을 직접 실행할 권한을 얼마나 갖는지, 외부 연동을 통해 들어오는 입력을 얼마나 신뢰하는지 세 가지였다.
그래서 표준을 쓰기 전에 이 세 축을 기준으로 위험 요소를 먼저 나열했다 — 개인정보·자격증명·내부 인프라 정보가 프롬프트에 포함되는 경로, 생성된 코드에 테스트용 키가 그대로 남는 사례, 이슈·PR 코멘트·MCP로 연결된 외부 데이터를 통한 프롬프트 인젝션, 리뷰 없이 병합되는 취약점, 필요 이상으로 넓은 에이전트 권한, 코드베이스 전체를 통째로 외부 서비스에 전송하는 워크플로.

### 4.2. 기술적 가드레일과 표준안 설계
> 위험 경로마다 대응하는 기술적 통제를 매칭해, "하지 말라"가 아니라 "이렇게 막는다"는 형태로 정리했다.

각 위험 경로에 대응하는 기술적 가드레일을 매칭했다.
민감정보 노출과 시크릿 하드코딩에는 pre-commit·CI 단계의 시크릿 스캐닝과, `.env`·인증서·사설 키를 AI 도구의 컨텍스트 접근 범위에서 원천 제외하는 규칙을 매칭했다.
과도한 에이전트 권한에는 파일시스템·네트워크·배포 권한을 작업에 필요한 최소 범위로 제한하고 프로덕션 자격증명과 분리된 환경에서 실행하는 것을, 프롬프트 인젝션과 외부 연동 위험에는 MCP 등 외부 연동 대상과 권한 범위를 사전 승인 목록으로 관리하는 것을 매칭했다.
도구 자체도 통제 대상으로 넣어, 사용 가능한 AI 코딩 도구는 데이터 처리 정책·학습 데이터 사용 여부·리전/호스팅을 기준으로 사전 검토한 화이트리스트로 관리하고, 계정은 개인 이메일이 아닌 회사 SSO로 연동하도록 했다.
보안 프롬프트 표준에는 민감정보를 마스킹하거나 예시 데이터로 대체하는 지침, 운영 시스템에 직접 영향을 주는 작업을 프롬프트만으로 자동 실행하도록 위임하지 않는다는 원칙을 담았다.

### 4.3. 외부 프레임워크와 대조 검증
> OWASP·NIST 프레임워크와 대조해, 사내 관점에서만 위험을 나열했을 때 놓치기 쉬운 항목을 보완했다.

OWASP Top 10 for LLM Applications, NIST AI Risk Management Framework와 초안을 대조해 누락 항목을 점검했다.
사내 워크플로 관점에서 나열한 위험은 "무엇이 새는가"에 집중돼 있었는데, 외부 프레임워크는 여기에 더해 생성 결과물 자체의 신뢰성(라이선스 불분명한 외부 코드 인용, 보안에 민감한 로직은 AI 생성 여부와 무관하게 별도 검토)과 사고 발생 시 대응 절차까지 다루고 있어 이 부분을 표준안에 추가로 반영했다.

---

## 5. 성과 및 배운 점
- 일반론적인 "AI 사용 정책"이 아니라, 실제 위험 경로(무엇이 새는지·에이전트가 뭘 할 수 있는지·외부 입력을 얼마나 신뢰하는지) 하나하나에 대응하는 기술적 가드레일을 매칭하는 방식으로 표준안을 구성했다.
- 이 표준안을 만드는 과정 자체가 AI 코딩 도구를 실제로 활용해 여러 보안 자동화 프로젝트를 만들어 본 경험(민감정보를 컨텍스트에서 제외하는 방식, 결과물을 사람이 검증하는 절차)을 반영한 것이었다 — 정책을 먼저 정하고 도구를 나중에 쓴 것이 아니라, 실제로 도구를 쓰면서 필요하다고 느낀 통제를 표준으로 정리한 순서였다.
- 외부 프레임워크(OWASP, NIST)는 사내 관점만으로는 놓치기 쉬운 항목(생성 결과물의 라이선스·신뢰성, 사고 대응 절차)을 보완하는 데 유용했다.
- 이 표준은 v0.1 초안이며, 사내 도구 사용 현황(어떤 도구를, 어떤 팀이, 어떤 범위로 쓰고 있는지)에 맞춰 섹션별로 검토·조정하는 것을 다음 단계로 남겨뒀다.
