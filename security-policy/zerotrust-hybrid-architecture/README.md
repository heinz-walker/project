<h1>제로트러스트 기반 하이브리드 보안 아키텍처 제안</h1>
<i>Zero Trust Architecture Proposal for a Hybrid (On-Prem + Cloud) Environment</i>
</div>

*2025.11 · 정보보안 담당*

---

## 1. 요약
망분리를 완화하면서도 기존과 동일하거나 그 이상의 보안 수준을 유지하기 위해, 인증·접근 체계를 제로트러스트 원칙("네트워크 위치가 아니라 신원과 상태를 매번 검증한다") 기반으로 재설계하는 제안서를 작성했다.
기존에 검토되던 경량 디렉터리 서비스 기반 인증 방식이 왜 이 요구를 충족하지 못하는지 실제 사례로 논증하고, 단말 검증·역할 기반 접근·자동 권한 재구성이 가능한 인증 체계로의 전환을 제안했다.
Bastion 세션 로깅의 구조적 결함을 계기로 접속 통제 자체를 다시 설계할 필요성도 함께 짚었고, 커널 레벨 은닉형 악성코드 대응·통합 모니터링(SIEM)·방화벽 정비를 포함한 단계적 로드맵으로 정리했다.

---

## 2. 배경
망분리 의무의 법적 근거가 바뀌면서, 위험 기반으로 인터넷망 차단의 예외를 허용할 수 있는 길이 열렸다.
문제는 "망분리를 완화하면 그만큼 보안 수준이 떨어지는 것 아니냐"는 우려였다 — 망분리라는 물리적 경계가 지금까지 사실상의 보안 경계 역할을 해왔기 때문이다.
망분리를 푸는 대신 그 경계가 하던 역할을 신원·단말·정책 기반의 상시 검증으로 대체해야 한다는 것이 이 제안의 출발점이었다.
그런데 검토 중이던 인증 체계(경량 디렉터리 서비스 기반)로는 단말 검증이나 세밀한 권한 통제가 구조적으로 불가능해, 망분리를 풀었을 때 그 공백을 메울 수 없다는 문제를 먼저 짚어야 했다.

---

## 3. 담당 역할
- 기존 인증 체계의 한계 진단 — 실제 접속 통제 취약 사례를 근거로 한계 분석
- 인증 체계 대안 비교·설계 — 제로트러스트 관점에서 두 인증 체계 대안 비교, 도입 방식별 비용 구조 검토
- 접속 통제 재설계 — Bastion 세션 로깅 구조의 결함 분석 및 개선 방향 제시
- 종합 로드맵 수립 — 인증·네트워크·모니터링을 포함한 단계적 도입 계획과 경영 리스크 정리, 제안서 작성 및 보고

---

## 4. 진행 과정
### 4.1. 기존 인증 체계의 한계를 실제 사례로 진단
> "경량 디렉터리 서비스로 바꿔도 되지 않느냐"는 질문에, 실제로 접속 통제가 뚫렸던 사례 세 가지로 답했다.

업무망 유선 구간이 고정 IP 기반으로 운영되고 있었는데, 이는 제로트러스트의 기본 전제("네트워크 자체는 신뢰하지 않는다")를 정면으로 위반하는 구조였다 — IP만 알면 인가되지 않은 단말도 접속을 시도할 수 있고, MAC 기반 필터링도 우회가 가능했다.
무선 구간도 공용 비밀번호 방식으로 운영돼, 비밀번호만 알면 임직원이 아니어도 접속 가능하다는 같은 유형의 문제가 있었다.
조직 개편으로 담당 업무가 바뀐 인원의 이전 접근 권한이 자동으로 회수되지 않고 수작업 변경에 의존하고 있다는 점도 확인했다 — 권한이 신원·역할 변화에 따라 자동으로 재구성되지 않는 구조였다.
경량 디렉터리 서비스는 계정 정보를 저장하는 기능은 있어도 단말 상태를 검증하거나 역할 기반 정책을 강제하는 기능 자체가 없어, 이 세 가지 문제 중 어느 것도 구조적으로 해결할 수 없었다.

### 4.2. 인증 체계 대안 비교와 결론
> 계정 저장소 역할만 하는 방식과, 신원·단말·정책을 통합 관리하는 방식을 제로트러스트 적용 가능성 기준으로 비교했다.

두 인증 체계 대안을 "신원(누구인가) · 단말(어떤 기기인가) · 정책(어떤 조건에서 접근 가능한가)"이라는 제로트러스트의 세 가지 축으로 비교했다.

| 축 | 경량 디렉터리 서비스 | 통합 디렉터리 서비스(도메인 기반) |
| --- | --- | --- |
| 신원(Identity) | 계정 저장만 가능 | 강한 인증 프로토콜 기반 통합 인증 |
| 단말(Device) | 단말 속성 검증 불가 | 단말 등록·정책 준수 여부 검증 가능 |
| 정책(Policy) | 중앙 강제 불가 | 그룹·조직 단위 정책을 중앙에서 강제 가능 |
| 조직 변화 대응 | 수작업 재구성 필요 | 역할·조직 변경에 따른 권한 자동 재구성 가능 |

경량 디렉터리 서비스는 초기 구축 비용이 낮다는 장점은 있지만, 조직 규모가 커지고 원격 근무·다양한 접속 경로가 늘어날수록 운영 부담이 급격히 커지는 구조였다.
반면 통합 디렉터리 서비스는 초기 도입 비용은 있지만 단말 검증과 정책 자동화까지 포함해 제로트러스트를 실제로 구현할 수 있는 유일한 현실적 대안이라는 결론을 냈다 — 이 판단에는 조직 규모, 특정 OS 비중, 개인정보 처리 여부, 원격 근무 시행 여부 같은 회사의 실제 조건을 함께 반영했다.

### 4.3. "기존 매체제어 솔루션으로 충분하지 않은가"에 대한 반박
> 매체제어·행위 통제 솔루션과 통합 디렉터리 서비스는 역할이 다르다는 것을 표로 정리해 설득 논리를 만들었다.

예상되는 반론은 "이미 쓰고 있는 매체제어·DLP 솔루션으로 단말 정책을 통제할 수 있는데 굳이 새 인증 체계가 필요한가"였다.
반박 논리는 역할 구분이었다 — 매체제어 솔루션은 사용자의 특정 행위(파일 반출, 매체 연결, 화면 캡처)를 감시·차단하는 도구이고, 통합 디렉터리 서비스는 단말 자체의 신원을 보장하고 조직 구조 기반 접근 정책을 중앙에서 강제하는 역할이라 서로 대체 관계가 아니라 보완 관계라는 것을 표로 정리해 제시했다.

### 4.4. Bastion 접속 통제의 구조적 결함과 재설계
> 기존 Bastion 세션 로깅 방식이 사용자가 스스로 종료시킬 수 있는 구조라는 것을 확인하고, 세션 관리형 서비스 기반으로 전면 전환을 제안했다.

기존에는 Bastion 접속 시 터미널 세션을 로컬 프로세스로 기록하는 방식을 쓰고 있었는데, 이 방식은 사용자가 그 기록 프로세스 자체를 직접 종료시킬 수 있어 원하는 시점부터 행위 기록을 남기지 않을 수 있는 구조적 결함이 있었다.
로컬 파일 기반이라 로그가 조작·삭제될 가능성도 있어, "접속했다"는 사실은 남아도 "접속해서 무엇을 했는가"는 사실상 추적할 수 없는 상태였다 — 감사 관점에서 있으나 마나 한 로그였다.
개선 방향으로는 로컬 프로세스 기반 로깅을 폐기하고, 클라우드 세션 관리형 서비스로 접속 자체를 대체해 명령어 단위 기록이 사용자 권한 밖의 중앙 저장소에 변조 불가능한 형태로 남도록 하는 방식을 제안했다 — SSH 키를 나눠 갖는 방식 자체를 없애고, 신원 기반 인증으로 세션을 여는 방식으로 접근 경로 자체를 바꾸는 것이 핵심이었다.

### 4.5. 종합 로드맵과 단계적 도입 계획
> 인증 체계 전환을 중심에 두고, 커널 레벨 위협 대응·통합 모니터링·네트워크 정비를 포함한 종합 로드맵으로 정리했다.

인증 체계 전환 외에도, 커널 레벨에서 동작해 기존 보안 솔루션으로 탐지하기 어려운 은닉형 악성코드에 대한 사전예방·런타임탐지·네트워크탐지·자동격리 4단계 대응 체계, 전사 로그를 한곳에서 상관분석할 수 있는 통합 모니터링 체계, 노후화돼 교체 시점이 다가온 방화벽의 통합 운용 방안을 함께 로드맵에 담았다.
현재 상태를 유지할 경우의 리스크(통제되지 않는 단말·계정·네트워크, 커널 레벨 위협에 대한 탐지·포렌식 불가, 인증심사 리스크)도 함께 정리해, "아무것도 하지 않는 것"이 가장 큰 리스크라는 점을 경영 보고에 반영했다.
도입 방식별 비용 구조도 함께 비교해, 조직 규모를 고려했을 때 현실적으로 감당 가능한 수준의 초기 투자로 도입할 수 있다는 점을 근거로 덧붙였다.

## 5. 성과 및 배운 점
- "제로트러스트로 가야 한다"는 원론이 아니라, 실제로 뚫려 있던 접속 통제 사례 세 가지를 근거로 제시해 왜 지금 체계로는 안 되는지를 구체적으로 논증했다.
- 새 인증 체계 도입 제안에 예상되는 반론(기존 매체제어 솔루션으로 충분하지 않은가)을 먼저 파악하고, 역할 구분표로 미리 답을 준비해 제안의 설득력을 높였다.
- Bastion 로깅 방식의 구조적 결함(사용자가 스스로 기록을 중단시킬 수 있는 구조)을 발견한 것을 계기로, 단순히 그 결함 하나를 고치는 데 그치지 않고 접속 통제 체계 전체를 다시 설계하는 제안으로 확장했다.
- 인증·네트워크·모니터링처럼 서로 다른 영역의 개선을 하나의 원칙(신원·단말·정책을 매번 검증한다)으로 묶어 로드맵을 구성하면, 개별 조치들이 왜 같은 방향을 향하는지 설명하기 쉬워진다는 것을 확인했다.
